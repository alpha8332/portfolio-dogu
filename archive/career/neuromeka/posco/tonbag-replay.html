01

Replay Requirement & Execution Ownership

Robot Replay·안전 로직 — 전체 기능 개발 →

요구사항은 Visualization에서 선택한 task/episode의 동작을 실제 로봇으로 다시 확인하고, Stop을 누르면 실행을 중지하는 것이었습니다. 영상 플레이어를 재생하는 기능도, 학습된 policy를 추론하는 기능도 아니었습니다. 이미 수집한 HDF5에서 팔과 엔드이펙터의 실행에 필요한 값을 읽어 로봇 명령으로 변환해야 했습니다.

브라우저는 선택한 episode와 실행 요청을 전달하고, backend의 Replay manager가 실행 중인 dataset·robot·상태·중지 요청과 진행 위치를 관리하도록 구성했습니다. Stop은 화면 상태만 바꾸는 것이 아니라 재생 루프와 로봇 motion 정리까지 이어져야 했습니다. 이후 pause/resume과 시각화 cursor도 같은 진행 상태에 연결했습니다.

이 장은 톤백 양팔 적용 당시의 수정 과정을 다룹니다. 이후 여러 로봇과 세션으로 확장한 공통 Replay 엔진은 별도의 source 선택 정책과 실행 구조를 갖습니다.

03

Measured Motion vs Stored Command

같은 episode 안에서 구분한 데이터
데이터뜻Replay에서 확인할 질문
proprio의 q / p측정된 관절값 / 실제 task pose실제로 수행한 동작을 재생하려는가
control의 teleop_command저장 시점에 보유한 teleop target새 명령 이력인가, 마지막 값이 유지된 snapshot인가
control.gripper저장된 좌우 개폐 채널배열 순서와 실제 EE 소속이 일치하는가
timestampsample / control의 기록 시각사용한 command 또는 state와 같은 시간축인가

실패한 episode에서는 오른팔의 teleop target이 일정한 값으로 남아 있는데 실제 오른팔 pose는 이후에도 변하고 있었습니다. 이를 그대로 재생하면 로봇은 움직이는 궤적이 아니라 멈춘 목표를 계속 받게 됩니다. 따라서 해당 과제 경로를 실제로 기록된 task pose 우선, pose가 없을 때 command fallback으로 바꿨습니다.

이 선택은 제어 입력을 원래와 완전히 동일하게 복원한다는 의미가 아닙니다. 관측된 궤적을 새로운 실행의 목표로 삼는 것입니다. 무엇을 다시 보여주려는 기능인지에 따라 command와 feedback 중 선택이 달라져야 한다는 점이 핵심이었습니다.

04

Right Arm Stopped: Narrow the Failure Interval

처음에는 오른팔의 그리퍼가 닫히고 다음 동작이 이어지지 않는 것으로 보였습니다. source와 actual을 좌우 q·p와 개폐 이벤트로 나누어 비교하면서, 팔 단독 구간과 양팔 동시 구간, close 이전과 close–open 사이, open 이후를 따로 봤습니다. “오른팔 알고리즘이 다르다”는 가정보다 어느 구간부터 어떤 데이터가 멈추는가를 확인했습니다.

수정 이력과 그 수정만으로 충분하지 않았던 이유
순서조사·변경다음에 드러난 문제 또는 최종 판단
1그리퍼 entry 선택과 좌우 채널 해석 보강tool_index를 저장 채널 순서와 혼동해 좌우가 뒤바뀐 수정이 있었음. capture 순서 [left, right]로 바로잡음
2변하지 않은 target 전송 생략호출 수는 줄었지만 hold target 재전송도 사라짐. 이 최적화는 해당 경로에서 제거
3sample마다 전송 유지, 양팔 전송 순서 교대항상 오른팔이 두 번째가 되는 편향을 완화해도 stale target 자체는 해결되지 않음
4teleop target과 측정 pose를 구간별로 대조오른팔 target은 일정하지만 proprio pose는 변하는 것을 확인
5해당 과제 경로에서 기록 pose를 우선 사용재생 대상을 마지막 command가 아닌 실제 수행 궤적으로 맞춤

변하지 않은 값을 생략하는 최적화는 일반적인 중복 제거처럼 보였지만, 이 경로에서는 같은 목표를 다시 전달하는 동작까지 제거했습니다. 더구나 target 자체가 갱신되지 않은 episode라면 재전송을 늘리는 것만으로도 정답이 될 수 없었습니다. dispatch 정책과 source 의미는 서로 다른 수정 축이었습니다.

05

Arm Identity & End-Effector Routing

좌우 그리퍼는 단순히 리스트의 첫 장치를 택할 수 없었습니다. 저장 배열의 채널 순서와 device registry의 arm·robot reference·channel을 함께 해석해 실제 장치 entry를 찾아야 했습니다. 이 과정에서 controller의 tool index와 capture 배열의 순서를 같은 것으로 본 실수를 수정했습니다.

Dual NURI가 12관절 양팔이라는 사실도 raw record를 12개씩 잘라 보내면 된다는 뜻은 아니었습니다. joint 값과 task pose는 표현이 다르고, left/right segment와 단위, gripper channel이 별도로 정해져 있습니다. 재생 로더에서 source의 의미를 해석한 다음 실제 명령 경로로 보내야 했습니다.

양팔 명령이 같은 source sample에서 나와도 RPC를 순차 호출하면 두 팔의 명령 도착은 완전히 동시가 아닙니다. 전송 순서 교대는 고정 순서의 편향을 줄이는 조치였으며, controller 수준의 원자적 양팔 명령이나 하드웨어 동기화를 구현했다고 표현하지 않았습니다.

06

Absolute Scheduling & Pause Semantics

톤백의 인장·재파지 순서를 다시 확인하려면 양팔 pose뿐 아니라 그리퍼 개폐 시점도 함께 보아야 했습니다. source와 재생 중 다시 수집한 actual을 비교할 때는 기록 시작·종료의 정지 여유 구간을 실제 조작 구간과 나누었습니다.

07

Physical Replay & Source / Actual Comparison

actual 수집은 Data Collection에서 Start를 누르고 Stop을 누르는 구간 전체를 포함합니다. 따라서 source와 actual 파일의 총 길이 차이만으로 재생이 늦어졌다고 결론내리지 않았습니다. 실제 동작 구간을 정렬한 뒤 좌우 q·p의 변화와 gripper 전환 전후를 비교했습니다.

코드를 수정한 뒤에는 UI server를 재시작하고 같은 source로 actual을 새로 수집해야 했습니다. 수정 이전 actual은 문제 재현 자료일 뿐 수정 효과를 확인한 결과가 아니었습니다. 로더·채널 매핑·전송·스케줄에 대한 회귀 검사를 추가하는 작업과 실제 로봇 동작 확인을 나누어 수행했습니다.

과제 적용에서 다시 실행해 확인한 동작
동작확인 맥락
Straight / Circle수집한 양팔 작업 동작의 실로봇 재실행
Knot / Ring양팔과 엔드이펙터가 함께 관여하는 동작 재실행
Shoveling선택 episode를 이용한 작업 동작 재실행

Dual NURI에서 위 동작의 Replay를 실제로 확인하고 시연했습니다. 작업별 세부 조건·영상·버전별 평가는 별도 기록 범위입니다. 정상 재실행을 확인한 사실을 정량적인 궤적 오차 보장으로 바꾸지는 않습니다.

08

Requirement, Implementation & Review

Replay 요구는 과제 담당자에서 그룹장을 거쳐 제게 전달됐습니다. 저는 선택 episode의 실행과 상태 제어를 구현하고 실제 장비에서 문제를 재현·수정했습니다. 완성 후에는 고객·그룹장·동료에게 실제 동작을 보여주고 검토와 승인을 받았습니다.

공통 Replay 장은 엔진의 전체 제어 구조를 설명하고, 이 장은 톤백 양팔에서 무엇이 잘못 해석됐고 왜 수정 방향이 바뀌었는지를 남깁니다. 같은 기능이라도 공통 API 설명만으로는 특정 episode에서 발생한 데이터 의미의 문제를 전달하기 어려웠기 때문입니다.

09

Engineering Note

이 작업에서 가장 큰 전환은 “오른팔이 왜 안 움직이지?”를 “지금 오른팔을 움직이게 하는 값은 무엇이지?”로 바꾼 것이었습니다. 숫자가 있고 형태가 맞아도 그 값이 과거의 target이면, 로봇은 기록한 동작이 아니라 그 target을 충실히 따라갈 수 있습니다.

또한 수정 하나의 성공 여부를 함수 테스트로만 판단하지 않게 됐습니다. 중복 전송 생략은 호출 관점에서는 합리적이어도 실제 hold 동작을 깨뜨렸습니다. 최적화할 때 무엇을 보존해야 하는지 먼저 정하고, source·dispatch·실제 상태를 연결한 새 실행으로 확인해야 한다는 것을 배웠습니다.
