ACT Temporal Ensembling

Technical Report

ACT의 Temporal Ensembling을 MiMicX 추론 runtime에 구현했습니다. 매 inference step에서 새 action chunk를 예측하고, 서로 다른 관측에서 같은 실행 시점을 예측한 값을 모아 로봇 명령으로 연결했습니다.

양팔 핸드오버에서는 팔이 부드러워져도 grasp를 놓쳤습니다. 가중치 조정에서 출발해 출력의 의미와 사건의 시간 순서를 추적했고, 연속 궤적·회전·grasp 사건의 결합 규칙을 분리했습니다. 논문의 원리, 플랫폼에 적용한 구조, 수정이 한 번에 끝나지 않았던 이유를 함께 설명합니다.

1. 문제와 연동 범위

1.1 ACT and TE: Learning a Chunk, Executing Its Predictions

ACT는 현재 관측에서 미래 action sequence를 예측하도록 학습합니다. 원 논문의 정책은 이미지·관절 상태와 latent를 조건으로 chunk를 생성하며, 학습 전용 CVAE encoder와 실행 정책을 구분합니다. TE는 학습 loss가 아니라, 이미 학습된 정책의 중첩 예측을 실행 때 결합하는 절차입니다.[ACT]

직접 구현한 범위는 MiMicX inference worker의 fresh-chunk 실행 경로, absolute-step bank, 출력 종류별 결합, 실행 guard, 설정 저장·복원과 진단입니다. ACT와 Temporal Ensembling 자체를 새로 제안한 것은 아닙니다. 또한 TE를 사용하기 위해 데이터셋을 다시 변환하거나 checkpoint weight를 재학습하는 경로를 추가하지 않았습니다.

1.2 Why Draining a Chunk Was Not Enough

기본 ACT provider는 action_horizon을 chunk_size와 n_action_steps에 연결했습니다. TE가 꺼진 실행은 관측 하나로 chunk를 만들고 queue에서 action을 차례로 소비합니다. 계산을 반복하지 않는 장점이 있지만, chunk 뒤쪽을 실행할 때도 예측의 근거는 처음의 관측입니다. 물체가 움직이거나 grasp가 바뀌어도 새 관측을 정책에 반영하기까지 기다리는 구간이 생깁니다.

양팔 핸드오버에서는 접근하는 궤적과 물체를 잡고 놓는 시점이 함께 맞아야 했습니다. 한 chunk가 끝나고 다음 관측으로 다시 예측할 때 target이 바뀌는 현상과, chunk 안에서 오래된 예측을 계속 쓰는 현상을 분리해 보았습니다. TE는 매 step 새 관측을 반영하면서 이전 계획의 현재 시점 예측도 함께 사용하는 선택이었습니다.

1.3 Integration Boundary: Runtime, Not a Vendor Toggle

기존 vendor ACT에는 temporal_ensemble_momentum 설정 흔적이 있었지만, task-space·multi-step 조건의 제한과 미구현 실행 분기가 남아 있었습니다. 설정 이름이 있다는 것과 MiMicX의 로봇·핸드 출력을 처리하는 기능이 있다는 것은 달랐습니다. vendor 내부의 옵션을 억지로 켜는 대신, 배포 상태와 장치 명령을 소유한 runtime에 별도 엔진을 두었습니다.

이 선택으로 모델은 chunk를 예측하고, executor는 출력 복원과 key 분할을 맡으며, TE 엔진은 현재 step의 후보 결합을 맡게 했습니다. 좌우 장치 연결, task-space 명령 생성과 장치 dispatch는 기존 경계를 재사용했습니다. TE가 새 명령 전달 체계를 만드는 대신, 기존 명령 경로 앞에서 하나의 action dictionary를 공급하도록 한 것입니다.

TE는 ACT의 추론 옵션입니다. Diffusion은 별도 model family이고, RTC는 별도 실행 전략입니다. 이 세 가지를 같은 smoothing 옵션처럼 다루면 checkpoint 호환성과 runtime 상태의 의미가 섞이므로 실행 전 검사에서도 구분했습니다.

2. 시간 정렬과 실행 구조

2.1 Temporal Alignment: Same Target Time, Different Queries

query q에서 만든 chunk를 A^(q), 현재 실행 step을 t라고 두면 선택할 원소는 A^(q)[t−q]입니다. 같은 배열 offset을 평균하는 것이 아닙니다. query마다 시작 시간이 다르므로, 절대 실행 시점이 같은 원소를 모아야 합니다. 원 논문의 Temporal Ensemble과 공식 eval 구현도 이 시간 정렬을 사용합니다.[ACT][ACT-CODE]

C(t)={A(q)[t−q]∣0≤t−q<Hq}현재 실행 step에 속하는 후보 집합

q와 t는 inference loop의 논리 step이고, offset은 0부터 시작합니다. H_q는 query q가 반환한 chunk 길이입니다. 예제의 10·11·12는 초 단위 timestamp나 로봇 관절의 각도가 아닙니다. 과거 시점에 실행한 action을 평균하는 일반적인 이동평균과도 다릅니다.

2.2 Action Bank: Append, Select, Prune and Preview

엔진은 query_step과 step별 action dictionary 목록을 한 묶음으로 저장합니다. worker가 q를 증가시키며 append하므로 후보 순서는 오래된 query에서 최신 query 순서입니다. 현재 t에 대해 offset=t−q를 계산하고 0≤offset<H_q인 항목만 사용합니다. q+H_q≤t인 chunk는 더 이상 현재나 미래의 action을 제공하지 못하므로 제거합니다.

H=4, 현재 step=12의 선택 예
query q담당하는 stepoffset / 상태
88–11만료: bank에서 제거
1010–132: 현재 후보
1111–141: 현재 후보
1212–150: 현재 후보
1313–16아직 생성되지 않은 미래 query; 포함하지 않음

처음부터 후보가 H개인 것은 아닙니다. 매 step 하나씩 같은 길이의 chunk를 추가하면 후보 수는 1부터 늘어나 최대 H개가 겹칩니다. 후보가 하나일 때에도 engine은 action을 반환하지만, 여러 예측을 결합한 상태는 아닙니다. 그래서 source_count와 overlap_active를 별도로 표시했습니다.

유효성은 action 값이 0인지로 판정하지 않습니다. 위치 delta=0이나 close target=0도 의미 있는 예측이기 때문입니다. 현재 구현은 chunk의 존재와 offset 범위로 후보를 고릅니다. 일부 key가 없는 후보는 해당 key의 평균에서 빠지고 남은 weight를 다시 정규화합니다. 이 처리가 입력 schema 전체의 정합성 검증을 대신하지는 않습니다.

Simulation preview는 현재 bank로 미래 step의 action을 미리 계산합니다. 앞으로 들어올 관측과 새 query까지 예측한 결과는 아닙니다. 실행 중 bank는 매 step 갱신되므로 preview 전체를 확정 궤적이나 실제 움직인 경로로 해석하지 않도록 했습니다.

2.3 Execution Architecture: Observation to Device Command

worker는 live robot state와 camera frame을 가져와 freshness와 동작 상태를 검사한 뒤 observation을 구성합니다. TE on에서는 queue에서 다음 값을 꺼내지 않고 compute_action_chunk로 모델을 새로 질의합니다. 반환한 chunk를 step별 dictionary로 분할하고 현재 query_step과 함께 bank에 넣은 다음, 그 step의 action을 결합합니다.

결합 뒤에는 action clamp와 유한값 검사를 적용하고, 다음 입력에서 사용할 이전 gripper·hand 명령 상태를 갱신합니다. command builder가 현재 로봇 자세와 장치 소속을 바탕으로 명령을 만듭니다. 실제 전송 전에는 teleoperation readiness와 엔드이펙터 preflight 등 기존 실행 조건을 통과해야 합니다. TE 엔진이 장치 연결이나 물체 파지를 직접 판단하지는 않습니다.

모델이 반환하는 success/progress scalar는 fresh query의 값을 worker에서 사용합니다. 여러 chunk의 action을 합치는 규칙을 그대로 적용하지 않았습니다. 보조 head가 있는 모델에서 출력의 역할이 다르기 때문입니다. progress 표시와 success threshold에 의한 종료 판정도 같은 의미로 취급하지 않습니다.

ACT executor는 모델의 정규화된 출력을 그대로 평균하지 않습니다. task-space head의 6D 회전을 3×3으로 복원하고 위치를 역정규화한 뒤, checkpoint의 action key 순서대로 분할합니다. TE가 회전당 9개를 다루는 이유는 이 복원 뒤에 있기 때문입니다. 6개 회전 feature를 6자유도 관절 각도로 오해하면 적용 위치부터 달라집니다.

엔진은 key별로 같은 표현의 값을 결합합니다. 좌표 변환이나 m↔mm 변환을 TE 안에서 임의로 수행하지 않았습니다. 장치 스케일과 key 의미가 잘못 연결된 상황을 평균으로 보정할 수는 없으므로, 출력 계약과 command builder의 경계를 함께 확인했습니다.

3. 가중치·회전·상대 동작

3.1 Schedules: Paper Weighting and MiMicX Weighting

ACT 원 논문과 공식 eval 코드는 oldest를 i=0으로 두고 exp(−m·i)를 사용합니다. 양수 m에서는 오래된 후보가 더 무겁습니다. MiMicX의 exp는 같은 식이 아니며, 후보 순서도 명시해야 실제 의미를 해석할 수 있습니다.[ACT][ACT-CODE]

at=∑i=1Nwici,wi=ri∑j=1Nrj연속 vector의 정규화 가중합
ri={1onesiNlinear1−exp(−αiN)expMiMicX raw weight：i=1…N，oldest → newest

c_i는 현재 실행 시점을 예측한 후보 vector, N은 현재 overlap 수입니다. 먼저 raw weight r_i를 만들고 합이 1이 되도록 나눕니다. ones는 동일 비중이고 linear는 최신 후보까지 선형으로 증가합니다. 로컬 exp는 증가하되 1로 포화하므로, “지수식이니 linear보다 항상 최신값을 더 강하게 쓴다”는 설명은 맞지 않습니다.

구현식 계산 예：후보 값 [1, 2, 10], N=3, oldest → newest
scheduleraw weight정규화 weight결합 결과
ones1, 1, 10.333 / 0.333 / 0.3334.333
linear1/3, 2/3, 10.167 / 0.333 / 0.5005.833
exp, α=11 − exp(−αi/3)0.202 / 0.347 / 0.4515.404
exp, α=41 − exp(−αi/3)0.278 / 0.351 / 0.3714.687

표는 식을 검산하기 위한 무차원 예제입니다. 실제 로봇의 위치·속도 측정이나 성공률이 아닙니다. 논문의 m과 MiMicX의 α를 같은 sensitivity 값으로 대입하거나, 논문 설정값을 이름만 맞춰 복사하지 않았습니다.

3.2 Why Increasing Alpha Did Not Fix the Grasp

limα→0+wi=2iN(N+1),limα→∞wi=1N,α=0：wi=1Nα의 양의 극한과 구현의 α=0 fallback

α가 작고 양수이면 1−exp(−αi/N)≈αi/N이므로 정규화 뒤에는 linear에 가까워집니다. 반대로 α를 크게 하면 모든 raw weight가 1로 포화해 균등해집니다. 정확히 α=0에서는 raw 합이 0이 되므로 구현이 균등값으로 대체합니다. 따라서 0과 아주 작은 양수의 동작도 같다고 가정할 수 없습니다.

핸드오버 중 α를 4에서 5로 바꾸자 한 번 잘 동작했지만, 반복하니 다시 실패했습니다. N=2에서 비중은 약 46.8:53.2에서 48.0:52.0으로 바뀔 뿐입니다. 그 한 번을 튜닝 성공으로 해석하기보다, grasp 값이 어떤 후보에서 선택되고 실제 open/close로 어떻게 바뀌는지 추적했습니다. 수치 비중을 조정하는 일과 사건의 의미를 복구하는 일은 달랐습니다.

3.3 Orientation: A Matrix Average Is Not a Rotation

위치 vector의 가중평균은 같은 공간의 중간값이지만, 회전행렬 집합은 일반적인 vector 공간이 아닙니다. 각 후보 R_i가 정상적인 회전이어도 합 M=Σw_iR_i는 열벡터의 길이와 직교성을 보장하지 않습니다. 이 값을 그대로 다음 자세에 곱하면 회전 이외의 변형이 섞일 수 있습니다.

RTR=I,det(R)=1;예제 M：MTM=diag(0.5,0.5,1)정상 회전 조건과 평균행렬 예
M=UΣVT,R=Udiag(1,1,det(UVT))VT가중합을 SO(3)에 투영

구현에서는 각 9개 block을 3×3으로 reshape해 SVD를 수행하고 U·Vᵀ를 구합니다. determinant가 음수면 U의 마지막 열을 뒤집어 reflection을 제거합니다. 이는 가중 행렬에 가까운 정상 회전을 Frobenius 거리 기준으로 찾는 투영입니다. 회전각을 단순 평균하거나 SO(3)의 모든 경로에서 최적인 보간을 보장하는 것과는 다릅니다.

엔진은 길이가 9의 배수인 orientation에 이 처리를 적용합니다. 그 외 길이는 수치 평균으로 fallback하므로, “어떤 잘못된 회전 입력도 자동 복구한다”는 기능은 아닙니다. executor에서 복원이 끝난 회전 block이 전달되어야 하고, 회귀 검사에서는 RᵀR≈I와 det(R)≈1을 각각 확인했습니다.

3.4 Relative Actions and the Live-Pose Boundary

MiMicX의 task-space relative action은 실행 시의 end-frame delta입니다. TE는 같은 target step의 delta 값끼리 결합하고, command builder가 현재 live pose를 사용해 실제 target으로 바꿉니다. 과거 query의 모든 delta를 먼저 world-frame 절대 자세로 바꾼 뒤 그 자세를 평균하는 구조는 아닙니다.

p*=pnow+Rnowδp,R*=RnowδR명령 생성 시 현재 자세와 상대 출력을 합성

p_now와 δp는 m, R_now와 δR은 무차원 3×3 회전입니다. 로봇 상태의 위치 mm·자세 deg를 계산 표현으로 바꾸고, 합성한 target을 장치가 받는 단위로 되돌립니다. TE 자체가 새로운 좌표 보정이나 지연 보상을 수행하는 것은 아닙니다.

따라서 같은 step이라는 시간 정렬만으로 action의 의미가 모두 같아지는 것은 아닙니다. 오래된 관측에서 예측한 delta를 현재 자세에 적용한다는 실행 계약도 이해해야 했습니다. fresh query를 매 step 더하는 이유와, 출력 복원 뒤·명령 합성 앞에 TE를 배치한 이유가 이 경계에서 연결됩니다.

4. 파지 실패와 이벤트 보존

4.1 Failure: Smooth Motion, Missed Left-Hand Grasp

양팔 바나나 핸드오버에서 TE off는 동작이 거칠지만 grasp가 들어갔고, TE on은 팔이 부드러워져도 왼쪽 그리퍼가 물체를 잡지 못했습니다. 처음에는 왼팔 출력 key나 index mapping이 누락되었는지 의심했습니다. 그러나 모델 출력의 key 분할, TE, command 변환과 실제 gripper event를 따라가니 왼쪽 close 자체가 완전히 없는 상황과는 달랐습니다.

문제는 처음의 TE가 숫자로 된 출력을 모두 평균했다는 점이었습니다. gripper의 raw target은 이후 threshold·hysteresis로 open/close 동작에 대응됩니다. 현재 시점을 close로 예측한 후보에 open 후보가 섞이면 threshold를 넘지 못하거나 전환이 지연될 수 있습니다. grasp mode ID처럼 범주를 뜻하는 값은 평균 중간값이 다른 명령이 될 수도 있습니다.

4.2 Why Latest Still Failed: A Receding Close Edge

첫 수정은 gripper와 hand grasp primitive를 평균에서 빼고 최신 overlapping 후보를 쓰는 것이었습니다. 연속 궤적은 blend하고 사건 값은 모델이 예측한 값을 그대로 사용했으므로, 애매한 중간 명령을 만드는 문제는 줄일 수 있었습니다. 그러나 이것만으로 grasp가 복구되지는 않았습니다.

예를 들어 query 10이 step 11의 close를 예측했어도, step 11에서 새 query가 내놓은 첫 원소가 open이면 latest가 그 close를 덮습니다. 다음 query도 같은 형태라면 미래의 close는 매번 다시 계획되지만 현재의 명령으로 실행되지 않습니다. 후보의 값은 이산형으로 보존했지만, 사건이 발생할 순서를 보존하지 못한 것입니다.

최종적으로 gripper·grasp primitive는 현재 step을 포함하는 가장 오래된 후보를 선택하도록 바꿨습니다. “첫 query의 첫 action을 계속 사용한다”는 의미가 아닙니다. 해당 query의 offset=t−q를 따라가고, 만료되면 다음 surviving query로 넘어갑니다. 계속 새로 쓰이는 step 0의 결정이 이전 계획의 현재 사건을 덮지 않도록 한 선택입니다.

5.4 Reset and Timing Are Part of the Algorithm

bank는 현재 run의 과거 예측입니다. 모델을 다시 불러오거나 새 run을 시작할 때 이전 후보가 섞이면 시간 번호가 같아도 다른 관측·다른 정책의 값을 합치게 됩니다. 모델 load, run start/stop, chunking 변경, TE 설정 변경에서 bank를 reset하도록 연결했습니다. 새 run의 inference step도 0에서 다시 시작하고 첫 query는 1이 됩니다.

매 step fresh query는 계산 비용을 늘립니다. 여기서 step은 camera frame timestamp나 로봇 servo tick과 자동으로 일치하지 않습니다. 논리 step별 후보 정렬이 정확해도 추론이 느리면 실제 시간에서 관측 반영이 늦어질 수 있습니다. 실행 지연과 입력 freshness를 함께 봐야 하는 이유입니다.

Simulation preview는 bank 내부를 읽는 진단 경로이고 장치의 실제 동작 검증은 아닙니다. TE 역시 동기식 질의 경로이므로 RTC의 비동기 계획이나 지연만큼 chunk를 건너뛰는 기능을 구현했다고 설명하지 않았습니다. 실행 전략의 이름보다 언제 관측하고 언제 command를 내보내는지가 중요했습니다.

실기에서는 TE on에서 팔이 부드러워져도 grasp를 놓치는 현상을 확인했고, 사건 선택 수정 뒤 gripper 문제가 해결된 것을 확인했습니다. 이 결과는 해당 오류의 수정 확인입니다. “부드럽다”는 관찰과 task 전체 성공률을 같은 지표로 바꾸지는 않았습니다.

6.2 Comparing Execution Strategies Without Mixing Training Effects

TE 효과를 비교할 때 기준은 같은 ACT checkpoint입니다. 다른 데이터로 다시 학습한 모델과 비교하면 정책 자체의 변화와 실행 후처리의 효과가 섞입니다. 초기 자세·물체 위치·장치 구성도 맞추고 TE off/on만 바꾸는 방식으로 평가 조건을 잡았습니다.

핸드오버에서는 전체 성공뿐 아니라 접근, 첫 grasp, 전달, 반대손 grasp, place, 복귀를 나눠 볼 필요가 있습니다. 팔의 궤적 변화, grasp/release 사건, task 완수는 각각 다른 관측입니다. 예를 들어 jerk가 줄어도 물체를 놓치는 횟수가 늘면 개선이라고 말할 수 없습니다.

성공률·jerk·latency·영상별 비교 결과는 별도 실험 기록에서 다룹니다. 여기에는 직접 확인한 수정 과정과 실행 계약을 남겼습니다. α 변경 직후 한 번의 성공이나 예상 성공률을 반복 측정의 결과로 채워 넣지 않았습니다.

6.3 Engineering Note: Preserve the Meaning of a Prediction

이 작업에서 바뀐 기준은 움직임이 매끈한가보다, 의도한 사건이 제때 실행되는가를 먼저 묻는 것이었습니다. 팔의 경로는 좋아 보였지만 물체를 넘기는 순간은 사라졌습니다. 같은 숫자 배열 안에도 연속 궤적, 회전, 명령의 이름표와 전환 사건이 섞여 있었습니다.

첫 수정에서 평균을 제거하고도 문제가 남았던 이유는 값의 종류만 보았기 때문입니다. latest는 새 관측을 더 빨리 반영하지만, 새 계획이 이전 계획의 close를 계속 취소할 수도 있었습니다. 출력값의 의미뿐 아니라 그 값이 언제 실행되어야 하는지도 구현 계약이라는 점을 배웠습니다.

논문을 적용할 때도 원래 시스템의 joint target과 현재 시스템의 relative pose·grasp primitive를 동일하게 취급할 수 없었습니다. 알고리즘 이름을 가져오는 데서 멈추지 않고, 수식의 후보 순서와 실제 장치가 해석하는 명령까지 따라가야 했습니다. 튜닝을 더 하기 전에 의미가 보존되는지 확인하는 것이 이 작업 이후의 판단 기준이 되었습니다.
