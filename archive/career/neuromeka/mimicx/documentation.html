Technical Report

MiMicX의 개발 지식을 신규 개발자가 코드를 찾고, 변경하고, 검증할 수 있는 문서 체계로 정리했습니다. 기존 매뉴얼과 기술 기록을 재배치하고, 온보딩 5개 문서·시스템 흐름도·저장소 지도·첫 업무 체크리스트를 연결했습니다.

1. 시스템 이해와 책임 경계

1.1 The Problem: Knowledge Existed, but the Route Through It Was Unclear

MiMicX에는 로봇·장치 설정, 텔레오퍼레이션, 수집, 데이터 검사, 학습, 추론과 Replay가 연결되어 있었습니다. 한 화면의 오류도 JavaScript 표시 문제인지, backend 상태 문제인지, 장치 입력이나 저장 계약의 문제인지 나눠 봐야 했습니다. 버튼 사용법이나 파일 목록만으로는 이 시스템을 다음 개발자에게 전달하기 어려웠습니다.

기능 설명, 구현 중의 계획, 장애 분석, 과거 인수인계와 운영 절차도 서로 다른 시점에 쌓였습니다. 같은 기능의 설명이 여러 곳에 있으면, 내용이 많은 것보다 어느 설명이 현재 기준인지 결정하기 어려운 것이 더 큰 문제가 됩니다. 새 기능을 추가할 때 어느 문서를 고쳐야 하는지도 모호했습니다.

직접 수행한 범위는 기존 자료의 분류·이동과 링크 보정, 신규 개발자용 온보딩 작성, UI에서 코드·계약·검사로 이어지는 설명 구조, 운영·검증 절차의 정리입니다. 기존 매뉴얼은 재사용하고 보강했습니다. 모든 문서를 처음부터 새로 썼다거나, 문서에서 설명하는 모든 플랫폼 기능을 이 업무에서 구현했다는 의미로 합치지 않았습니다.

신규 개발자는 목적과 흐름을 먼저 알아야 하고, 기존 개발자는 변경 지점과 회귀 검사를 빨리 찾아야 합니다. 운영자는 실제 장비를 연결하고 문제가 생겼을 때 다음 확인 단계를 알아야 합니다. 같은 설명을 세 번 복사하기보다 독자별 진입점을 두고 공통 정의로 연결했습니다.

문서 구조의 기준도 작성한 날짜나 파일 형식보다 독자가 해결하려는 질문으로 잡았습니다. 개발 배경을 읽으려는 사람과 정확한 현재 payload를 찾는 사람에게 같은 긴 문서를 주면, 필요한 내용이 있어도 찾기 어려웠기 때문입니다.

1.3 Three Maps: Workflow, Runtime and Repository

첫째는 작업 흐름입니다. 설정에서 장치를 등록하고, 실제 입력과 움직임을 확인한 뒤 데이터를 수집합니다. 원본을 검사·선별하고 학습에 연결하며, 모델의 입출력과 현재 장치의 호환성을 확인한 뒤 실행합니다. Replay는 기록한 동작을 실행하는 별도 경로입니다. 화면의 순서만이 아니라 단계 사이에 무엇이 남는지를 설명했습니다.

둘째는 실행 구조입니다. Browser와 UI gateway, 장치·수집을 소유한 서비스, 데이터·학습 서비스, 모델 runtime은 서로 다른 책임을 가집니다. Host의 USB·GPU·desktop runtime과 container 내부도 구분해야 합니다. 공유 workspace가 있다고 프로세스 메모리까지 공유되는 것은 아니므로, live 상태는 명시적인 통신 경계를 통해 읽도록 설명했습니다.

셋째는 저장소 지도입니다. 화면 구조를 바꾸는 곳, 요청을 받는 곳, 상태와 정책을 소유한 곳, 재사용 가능한 package와 검사 위치를 연결했습니다. 작업 흐름도와 코드 지도를 같은 그림으로 뭉개지 않은 이유는 사용 순서가 곧 실행 프로세스나 수정 파일의 순서는 아니기 때문입니다.

2. 기술 설명과 진단 예시

2.1 A Worked Example: CapturePlan from Screen to Artifact

개발자 매뉴얼은 화면 위치, 사용자가 결정하는 것, 주요 조작, runtime 흐름, 관련 요청, backend 책임과 주의점으로 구성했습니다. 이 형식은 화면을 소개하려는 것이 아니라, 새 개발자가 한 기능을 위에서 아래로 추적하게 하려는 장치였습니다. 수집 계획인 CapturePlan을 대표 예제로 사용했습니다.

Task를 선택하면 backend가 저장된 계획을 읽거나 현재 구성에서 draft를 만듭니다. 화면은 필수·선택·사용 불가 stream과 canonical camera order, blocker와 warning을 표시합니다. 사용자는 선택 항목의 포함 여부를 바꿀 수 있지만, 화면에서 필수 행을 지웠다고 실제 수집 schema의 필수 데이터까지 제거되어서는 안 됩니다.

저장은 사용자 의도를 그대로 파일에 쓰는 작업이 아닙니다. Backend가 현재 장치·session과 함께 계획을 정규화하고 필수 stream을 복원합니다. 이미 episode가 있는 task에서 schema를 바꾸는 수정은 거부하고, 필요한 경우 새 task로 분기합니다. 계획 파일이 저장된 뒤에도 실제 수집 시작에는 별도의 preflight가 필요합니다.

이 단면을 설명할 때에는 기능의 개발 성과와 문서화 성과를 구분했습니다. 여기서 보여주는 것은 CapturePlan 자체를 새로 구현했다는 주장이 아니라, 화면의 조작이 어느 규칙을 거쳐 어떤 artifact로 남는지 설명한 방법입니다.

정상 경로만 적으면 오류 메시지가 나왔을 때 다시 코드를 처음부터 읽게 됩니다. 그래서 “이 버튼을 누르면 된다”에 더해, 무엇이 고정되어야 하고 어떤 조건에서 거부되는지 남겼습니다. 필수 stream 보존, 기록 이후 schema lock, episode의 task 소속은 화면 사용법 이상의 유지보수 조건입니다.

검사도 같은 규칙에 연결했습니다. 필수 행을 생략한 요청에서 필수 데이터가 유지되는지, 기존 episode가 있을 때 schema 변경이 막히는지, 새 task에 분기한 계획을 다시 읽을 수 있는지를 회귀 사례로 찾게 했습니다. 링크를 따라 테스트 파일을 여는 데서 끝내지 않고, 그 검사가 어떤 불변 조건을 보호하는지 설명했습니다.

Source of Truth는 모든 지식을 한 파일에 넣는다는 뜻이 아닙니다. 같은 사실의 현재 정의를 여러 파일에서 따로 관리하지 않는다는 규칙입니다. 예를 들어 schema는 값의 구조와 순서를, metadata는 어떤 장치·수집·변환·모델에서 나온 값인지 추적하는 정보를 설명합니다. 둘을 나누되, 한 artifact를 이해할 때 함께 찾을 수 있게 연결했습니다.

데이터의 shape만 적는 것도 충분하지 않았습니다. 관측과 명령의 구분, 장치 소속, 좌우·robot 순서, 단위·좌표계와 시간 기준이 달라지면 같은 길이의 배열도 다른 뜻이 됩니다. 정확한 필드 정의는 reference에 두고, 매뉴얼에서는 사용자가 그 차이를 어디서 확인해야 하는지 설명했습니다.

이 규칙이 문서와 코드를 자동으로 동기화해 주는 것은 아닙니다. 변경할 때 정의를 소유한 문서를 찾고, 구현과 검사에 대조해 갱신해야 합니다. 과거 handoff에 등장한 파일명이나 예전 단계의 계획을 그대로 현재 경로로 믿지 않도록, 현재 reference와 실제 호출 위치를 다시 확인하는 경로를 두었습니다.

2.4 Turn an Incident into a Diagnostic Procedure

EIR 설정 과정에서는 HMD·controller pose가 갱신되는데 trigger·squeeze·button이 0으로 남는 문제가 있었습니다. 처음 보는 사람에게 “OpenXR 문제였고 세팅을 고쳤다”만 전달하면 같은 상황에서 다시 추측해야 합니다. 기록에는 계층별 관찰과 다음 확인 기준을 남겼습니다.

중요한 구분은 값이 0이라는 것과 input action이 비활성이라는 것이었습니다. 정상적으로 활성화된 입력에서 버튼을 누르지 않은 0과, runtime이 그 action을 제공하지 않는 0은 다음 조치가 다릅니다. pose의 유효성, action 활성 여부, session focus, rendering과 swapchain 상태를 분리해 설명했습니다.

또한 debug script가 동작한다고 실제 application session도 정상인 것은 아니었습니다. 진단 프로그램을 동시에 실행하면 focus를 가져가 MiMicX의 입력 상태를 바꿀 수 있었습니다. 따라서 최종 확인은 실제 로봇 명령 경로가 사용하는 application session에서 하도록 정리했습니다. 관찰 도구가 대상의 조건을 바꿀 수 있다는 주의점까지 절차에 남긴 사례입니다.

장애 보고서에는 증상, 비교한 조건, 가설, 실제 관찰, 수정과 최종 확인을 구분했습니다. 이를 runbook에 옮길 때는 시행착오 전체를 복사하기보다, 다음 사람이 같은 증상을 만났을 때 어떤 관찰로 분기해야 하는지를 남겼습니다.

먼저 핵심 개발자 매뉴얼의 위치를 안정화하고 root 진입 문서와 매뉴얼 내부 링크를 수정했습니다. 그다음 reference, feature/runbook, 개발 배경·history/archive 순서로 이동했습니다. 파일 이름을 한꺼번에 바꾸고 본문까지 동시에 다시 쓰면, 어디서 링크가 끊기고 어떤 설명이 달라졌는지 검토하기 어려워 단계적으로 진행했습니다.

이동표에는 옛 경로와 새 위치를 모두 남겼습니다. 파일 삭제 없이 지식을 보존하면서, 당장 정리하기 어려운 연구성 문서나 인코딩이 손상된 자료는 current reference와 분리했습니다. 파일이 오래되었다는 이유만으로 유용한 실패 기록까지 없애지는 않았습니다.

3.2 Link Integrity and Historical References Are Different Checks

Markdown 링크는 문서가 있는 위치를 기준으로 해석됩니다. 같은 파일을 다른 directory로 옮기면 링크의 대상은 그대로여도 상대 경로가 달라질 수 있습니다. 그래서 옮긴 문서의 내부 링크뿐 아니라 그 문서를 가리키는 README·architecture·feature·개발 기록도 함께 확인했습니다.

이동 뒤 검사한 연결

구 경로가 검색된다는 이유로 모두 바꾸지도 않았습니다. Migration map의 “이전→이후” 대응과 history가 설명하는 당시 경로는 보존할 이유가 있습니다. 반대로 current manual이나 첫 읽기 안내가 낡은 파일로 이동하게 하면 수정해야 합니다. 문자열이 남아 있는가와 독자가 잘못 안내되는가는 다른 문제였습니다.

당시 링크 존재 검사는 구조 검증에 사용했습니다. 그러나 missing link가 없다는 결과가 설명의 최신성, 예제의 정확성, 독자의 이해까지 증명하지는 않습니다. 경로 검사와 내용 검토의 완료 조건을 따로 두었습니다.

초기에는 Purpose, Reading Order, Scope, Source Material, Out of Scope를 갖춘 skeleton을 만들었습니다. 이때 파일은 있어도 온보딩 본문은 완성되지 않았습니다. 이후 01·02의 목적·흐름, 03의 저장소 지도, 04의 실행·검사, 05의 첫 업무 순서로 내용을 채우고 진입 문서의 상태를 갱신했습니다.

3.4 Remove the Author’s Machine from the Procedure

처음 실행·검사 안내에는 특정 checkout, 개인 환경 이름과 interpreter 경로가 섞여 있었습니다. 작성자 PC에서는 통하더라도 다음 사람이 그대로 따라 하면 다른 저장소나 예전 editable package를 불러올 수 있습니다. 실행 명령이 문법적으로 맞는 것과 올바른 환경에서 실행되는 것은 달랐습니다.

공유 문서에는 대체할 값과 확인 기준을 적고, 한 작업의 검증 결과에는 실제 branch·commit·환경을 남기도록 했습니다. 공통 절차에서는 개인 정보를 제거하되 실행 결과의 추적 가능성은 유지한 것입니다.

기존 컨테이너가 이미 동작하는 PC에서 별도 개발 서버를 띄우는 경우도 구분했습니다. 잘못된 checkout이나 다른 runtime을 보고 있으면 수정 효과를 판단할 수 없기 때문입니다. 환경 확인을 단순 준비 단계가 아니라 검증의 일부로 다뤘습니다.

4. 운영 인수인계와 검증

4.1 Handoff as a Path to the First Reviewable Change

신규 개발자에게 모든 매뉴얼을 먼저 완독하게 하는 방식으로 구성하지 않았습니다. 제품과 실행 구조를 이해한 뒤 자신이 맡은 work area를 고르고, 관련 기준 문서·owner code·검사 위치로 들어가게 했습니다. 첫 작업은 무엇을 바꿀 것인지와 어디까지 검증할 것인지 설명할 수 있는 작은 단위로 잡았습니다.

첫 업무에서 남기도록 한 판단
단계질문전달할 결과
범위UI·계약·service·package·장치 중 무엇이 바뀌는가?최소 변경 범위와 영향 받는 경계
현재 정의어떤 문서가 이 동작을 소유하는가?reference·feature·관련 history
구현 위치누가 상태를 만들고 저장하는가?owner와 실제 호출 경로
검증이 수정이 맞다는 것을 무엇으로 확인하는가?focused test와 실제 장비 확인 조건
이관다음 사람이 무엇을 이어서 해야 하는가?변경·결과·제약·rollback·관련 문서

인수인계 기록에는 변경된 동작, 호환 경로, 저장 위치 변화와 필요한 검사를 남겼습니다. 예를 들어 preset의 영속 저장 위치와 runtime log 위치는 목적이 다릅니다. 예전 위치를 읽는 호환 처리가 있다고 새 값을 계속 옛 위치에 쓰는 것은 아니므로, 현재 경로와 이관 경로를 구분해 설명했습니다.

숙련 개발자를 위한 질문도 별도로 정리했습니다. 제품 lifecycle과 application state의 owner, split service의 쓰기 책임, motion 경로의 중단 조건과 rollback 같은 질문입니다. 현재 답과 후속 설계 과제를 나눠, 아직 검토할 내용을 이미 완성된 기능처럼 전달하지 않도록 했습니다.

4.2 Developer Workstation Preflight Is One Kind of Evidence

장치가 없는 개발 PC에서는 import, route/service, API 응답 모양, UI event wiring과 package 경계를 검사할 수 있습니다. 어떤 변경인지에 따라 집중된 검사를 고르고, 공통 경계가 바뀌었을 때 범위를 넓히도록 안내했습니다. 문서 이동은 링크와 파일 존재, 변경 diff를 따로 봅니다.

이 결과만으로 실제 카메라 timing, VR runtime focus, hand·robot SDK, 로봇 motion과 수집 품질을 확인했다고 적지는 않았습니다. 테스트 대역과 실제 입력은 다른 조건입니다. 개발 PC에서 통과한 검사와 실제 장비에서 남은 확인을 분리하면 다음 사람이 같은 범위를 다시 추측하지 않아도 됩니다.

정확한 테스트 명령은 Run And Test에 두고 첫 업무 체크리스트와 developer reference에서 연결했습니다. 동일 명령을 여러 문서에 복제하면 파일 이동이나 검사명 변경 때 서로 달라질 수 있기 때문입니다.

4.3 Robot PC Validation Needs Conditions, Observables and a Stop Rule

로봇 PC 확인에는 실행 중인 release와 workspace, 장치 구성, 입력과 중단 조건이 필요합니다. 같은 branch를 받았다고 실제 실행 프로세스도 그 코드를 쓰는 것은 아닙니다. 제품 설치 경로와 직접 Python 실행을 구분하고, customer-style 확인은 설치된 제품과 container 상태부터 보도록 정리했습니다.

실제 환경 확인을 재현 가능하게 남기는 항목
항목확인 내용남길 정보

환경올바른 workspace와 Host runtime을 보는가환경·장치 구성·필요한 runtime 상태
입력 준비현재 장치와 계약이 맞는가registration·readiness·fresh sample·compatibility

종료·복구문제 발생 시 무엇을 멈추고 되돌리는가stop 조건·실제 결과·관련 rollback

수집 변경이라면 짧게 start·stop·save한 뒤 metadata를 검사하고, 모델 실행 변경이라면 compatibility와 입력을 확인한 후 해당 실행 경로를 봅니다. 외부 모델도 bundle 검사·입력 preview·dry run과 live dispatch를 나눕니다. 모든 작업을 한 번에 시연하는 대신 변경한 계약을 입증할 수 있는 절차로 만들었습니다.

검증 요약에는 결과뿐 아니라 확인한 조건을 남기도록 했습니다. 다음 담당자가 실패를 이어받을 때 “동작함” 한 줄보다 어느 환경에서 어떤 입력으로 어디까지 확인했는지가 더 유용하기 때문입니다.

4.4 First Setup, Daily Operation and Stable Entry Points

장비 설치 문서에서는 최초 세팅과 매일의 사용을 구분했습니다. SDK·permission·pairing·물리 연결·calibration을 처음 준비하는 일과, 준비된 PC에서 장치를 켜고 상태를 확인하는 일은 다릅니다. 자동화 가능한 설치·검사와 사람이 해야 하는 물리·vendor 절차도 나눴습니다.

운영 정책이 바뀌면 예전 문서의 설명을 그대로 두는 것만으로 링크를 보존할 수는 없습니다. Customer First Setup의 상세 정책을 Device Packs runbook으로 모은 뒤, 기존 문서는 새 기준과 필요한 세부 절로 안내하는 안정된 진입점으로 남겼습니다. 예전 링크로 들어온 사람이 오래된 Host setup 가정을 계속 따라가지 않게 한 방식입니다.

이 사례는 과거 자료를 남기는 것과 과거 설명을 계속 현재 기준으로 유지하는 것이 다르다는 점을 보여줍니다. 삭제 없이도 현재 안내를 한 곳에 모으고 이전 진입 경로를 살릴 수 있었습니다.

실제 환경 확인 기록조건·입력·결과·복구 정보가 남음정량적 인수인계 효율이나 교육 효과

완성한 산출물은 문서 분류와 migration map, 신규 개발자 읽기 경로, 온보딩 본문, UI–backend 연결 형식, 시스템·저장소·학습 지도, 실행·검사·이관 체크리스트입니다. 초기 skeleton 이후 본문을 채운 이력과, 개인 환경 가정을 제거한 후속 수정도 구분해 남겼습니다.

이관을 마감할 때에는 root 진입 문서에서 새 읽기 경로를 따라갈 수 있는지, current 문서가 옛 위치를 계속 가리키지 않는지, 실제 존재하는 파일과 작성 예정인 파일이 구분되는지 확인했습니다. 이후 개인 환경 가정까지 걷어내면서 다른 workstation에서도 적용할 수 있는 안내로 정리했습니다.

유지보수를 이어갈 정보는 현재 동작뿐 아니라 아직 판단이 필요한 지점도 포함합니다. 그래서 현재 계약, 과거 변경 이유, 열려 있는 설계 질문을 서로 다른 위치에 남겼습니다. 다음 담당자가 해결된 문제를 다시 풀거나 검토 중인 안을 확정된 동작으로 받아들이지 않게 하기 위한 구분입니다.

5.3 Engineering Note: Transfer the Decision, Not Only the Answer

문서를 정리하면서 가장 크게 달라진 기준은 답을 남겼는가보다, 다음 사람이 그 답의 적용 조건을 판단할 수 있는가였습니다. 특정 PC의 실행 명령이나 “정상 동작했다”는 한 줄만 남기면 환경이 달라지는 순간 다시 사람에게 물어봐야 했습니다.

CapturePlan을 설명하려면 화면의 saved와 ready가 다른 상태라는 것을 알아야 했고, EIR 문제를 전달하려면 입력값 0과 input inactive를 구분해야 했습니다. 내가 이해했다고 생각한 기능도 owner, 정상 조건과 실패 분기를 적으려 하면 빈틈이 드러났습니다. 문서 작성은 시스템을 설명하는 일이면서 내 이해를 검사하는 과정이었습니다.

또한 좋은 인수인계는 현재의 정답만 넘기는 것으로 끝나지 않는다고 배웠습니다. 정확한 정의가 어디 있고, 무엇을 바꾸면 어떤 검사를 다시 해야 하며, 현재 답이 없는 부분은 무엇인지까지 남겨야 다음 변경이 이어집니다. 문서의 수보다 이 연결이 유지되는지를 더 중요한 완료 기준으로 삼았습니다.
