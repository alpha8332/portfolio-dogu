1. 플랫폼의 목적과 실행 구조

1.1 장치·데이터·모델 사이의 의미를 유지하는 개발

MiMicX는 사람의 조작으로 로봇을 움직이고, 그때의 상태·명령·영상을 수집해 학습과 실제 실행으로 연결하는 플랫폼입니다. 제 업무는 기존 플랫폼 위에서 입력 장치, 복수 로봇, 로봇손, 학습 정책과 실행 경로를 확장하고 통합 과정의 오류를 해결하는 일이었습니다.

확장의 어려움은 장치 하나를 연결하는 데서 끝나지 않았습니다. 핸드 관절이 파일에 저장돼도 학습 키로 변환되지 않으면 사용할 수 없고, 학습 출력에 손 값이 있어도 decoder에서 사라지거나 다른 로봇에 연결되면 실행되지 않습니다. 각 단계가 같은 로봇·같은 채널·같은 시간·같은 명령 의미를 가리키도록 맞추는 것이 공통 과제였습니다.

1.2 수집·학습·배포와 Replay를 다른 경로로 이해

실행할 행동의 출처
경로소비하는 것다음 행동을 만드는 방식
Native policy변환 데이터와 MiMicX 학습 checkpoint현재 관측에 조건화한 ACT / Diffusion 예측
External policy연구팀이 전달한 모델·processor·calibration·adapter외부 정책 추론 후 MiMicX 명령으로 변환

Replay는 학습 정책의 성공 여부를 시험하는 경로가 아닙니다. 반대로 외부 모델은 MiMicX에서 학습하지 않았어도 실행할 수 있습니다. 공통으로 필요한 것은 현재 장치의 소속과 상태, 명령 변환과 정지 경로입니다.

1.3 UI gateway와 세 실행 서비스의 상태 소유권

브라우저의 진입점은 UI gateway입니다. 장치 등록·텔레오퍼레이션·수집은 device-data, 데이터 검사·Replay·학습은 data-studio, native/external 추론은 model-runtime이 담당합니다. 단일 Python 서버로 실행하는 개발 경로와 달리 split 배포에서는 각 서비스가 별도 프로세스와 메모리를 갖습니다.

UI는 선택과 실행 의도를 보내고 backend가 반환한 상태를 표시합니다. 로봇 연결, 카메라 순서, 재연결과 명령 실행을 화면마다 판단하게 하면 탭을 바꾸는 것만으로 기준이 달라질 수 있습니다. 이런 상태는 backend가 소유하고, 필요한 화면들이 같은 계약을 소비하도록 했습니다.

1.4 공유 workspace가 공유 메모리를 뜻하지 않는 이유

같은 workspace를 mount하면 episode·checkpoint·calibration 파일은 함께 읽을 수 있지만, 다른 프로세스의 robot registry 변수가 복제되지는 않습니다. 그래서 장치 등록 화면에서는 로봇이 연결돼 보이는데 data-studio의 Replay는 로봇을 찾지 못하는 상황이 생길 수 있습니다.

이 경우 화면의 목록을 고치는 것으로 해결되지 않습니다. Replay를 처리하는 서비스가 장치 등록을 소유한 서비스에서 registry를 명시적으로 읽어 와야 합니다. 파일로 넘길 값과 실시간으로 조회할 값, 해당 작업이 소유할 runtime 객체를 먼저 나누는 것이 조사 순서였습니다.

1.5 직접 USB 접근과 Host VR bridge를 분리

SpaceMouse와 카메라는 container에서 장치 노드와 권한을 확보해 HID·영상 API로 접근하는 경로를 사용합니다. Vive와 Quest/Pico는 SteamVR 또는 WiVRn/OpenXR의 desktop session·GPU runtime에 의존하므로 Host에서 구동하고 bridge로 pose·button snapshot을 전달합니다.

USB 노드가 보이는지와 VR session이 focus·render 상태인지는 다른 문제입니다. 장치를 한 가지 container 접근 방식으로 통일하지 않고, 직접 접근에 필요한 장치 identity·권한과 Host bridge의 socket·shared memory·freshness를 각각 확인했습니다.

2. 장치 식별과 기록의 의미

2.1 이름·순서·소유자를 분리한 장치 식별

화면의 표시 이름과 배열의 첫 번째 위치는 물리 장치를 식별하는 충분한 근거가 아닙니다. robot_id는 운영자가 선택하는 항목이고 robot_key는 저장에 쓰는 안정된 소속입니다. 복수 로봇 session은 participant·robot_order·primary를 따로 유지하며, 그리퍼와 핸드도 어느 로봇에 달렸는지로 해석합니다.

단계 사이에서 유지하는 식별
대상계약유실될 때의 문제
Robot sessionparticipant / stable order / primary / robot_key선택한 로봇과 데이터·명령 대상이 달라짐
End effector소유 robot / segment / profile / joint count같은 길이의 손 명령을 다른 장치로 보냄
Cameracamera_key / slot_index / checkpoint camera_names학습과 실행의 시각 채널 순서가 바뀜
Dataset / model선택 원본·변환 설정·model family·IO metadata숫자 형상은 맞아도 다른 의미로 실행

카메라를 재등록하거나 목록의 표시 순서가 바뀌었을 때도 학습 입력의 의미는 유지돼야 합니다. 그래서 학습·배포 화면이 카메라 이름을 각각 추정하는 대신 backend의 canonical order와 checkpoint에 저장한 순서를 비교하도록 구성했습니다.

2.2 Start 요청에서 task CapturePlan과 저장 worker까지

수집 시작 시에는 이전 episode가 Save/Reject를 기다리는지, 이미 recording 중인지, 선택 로봇과 task가 유효한지 먼저 확인합니다. 이어 현재 구성과 task의 CapturePlan을 대조하고, 필수 stream과 선택한 camera·hand 등의 persisted key를 확정합니다.

CapturePlan은 화면 체크박스 목록 이상입니다. 어떤 로봇의 어떤 키를 저장할지, 필수 stream과 선택 stream을 어떻게 구분할지, 현재 구성 변경을 허용할지를 규정합니다. sample 시간축은 암묵적인 필수 필드이고 camera·FT·hand는 값에 대응하는 timestamp와 validity를 함께 가져야 합니다.

세션 metadata와 저장 writer가 준비된 뒤 capture worker를 시작합니다. 현재 보존본에는 capture sidecar를 선택적으로 사용하는 경로도 있어 직접 camera handler를 해제·복구하는 책임이 포함됩니다. 시작 실패 시 열린 세션을 정리해야 다음 녹화에 상태가 남지 않습니다.

2.3 측정한 상태와 보낸 목표를 다른 stream으로 저장

종류예시 의미학습·실행에 필요한 이유
proprio현재 joint·EE pose·velocity로봇이 실제로 어디에 있었는가
control발행한 task-space 목표·그리퍼 목표조작자가 무엇을 명령했는가

session metadata로봇 소속·순서·장치·capture plan과거 파일을 현재 설정 없이 해석

단일 로봇·기존 기록은 v4 top-level 키를 사용하고, 복수 로봇 session의 v5는 로봇별 stream을 robot.<robot_key> 아래에 둡니다. 공통 카메라와 sample 시간축은 상위에 남습니다. 같은 arm이라는 이름을 여러 로봇에서 사용해도 저장 namespace로 소속을 구분할 수 있어야 했습니다.

0으로 채운 teleop 목표는 일부 호환 경로에서 “이 step에 목표가 기록되지 않음”을 나타내는 placeholder입니다. 이를 실제 원점 목표로 학습하면 멈춰 있던 구간이 원점으로 움직이는 지시로 바뀝니다. 변환 단계에서는 이런 구간을 현재 pose 유지 의미로 해석해야 합니다.

2.4 Sample·camera·명령의 시간축과 유효성

sample의 monotonic timestamp는 같은 실행 안의 순서와 간격을 나타내고, UTC는 다른 기록과 시각을 맞추는 데 쓰입니다. 카메라 frame과 각 장치의 timestamp·validity는 그 sample에 담긴 값의 출처와 나이를 설명합니다. 같은 행에 저장됐다는 이유만으로 모든 센서가 같은 순간에 촬영·측정됐다고 볼 수는 없습니다.

전체 해상도 RGB는 주로 sidecar MP4로 저장하고 metadata의 video_files로 연결합니다. HDF5 preview가 존재하더라도 원본 영상과 같은 해상도·저장 경로라고 가정하지 않습니다. 파일 개수뿐 아니라 프레임 대응·누락·age·validity를 함께 봐야 상태와 영상이 어긋난 학습 샘플을 찾아낼 수 있습니다.

3. 원본에서 학습 산출물까지

3.1 Raw 보존 위에 curation과 전처리 선택을 얹기

Visualization에서 episode 제외, keep range·trim·quarantine·tag/note를 저장해도 raw HDF5와 영상은 유지합니다. Training은 어떤 curation ID와 어떤 원본을 선택했는지 받아 변환합니다. 원본을 직접 자르면 잘못된 제외를 되돌리거나 이전 run을 재구성하기 어려워집니다.

전처리에서는 teleop 시작 전 대기 구간, 카메라별 crop·resize, absolute/relative action, auxiliary label을 선택합니다. Crop 좌표가 저장됐는지와 crop_enabled가 켜져 실제 적용되는지는 별개입니다. 설정을 보존한 preset이 항상 잘린 영상으로 학습한다는 의미는 아닙니다.

3.2 Input/Output Mapping이 학습 문제를 정의

Input은 모델이 보는 관측이고 Output은 예측하도록 요구하는 행동입니다. 현재 pose와 기록한 teleop 목표를 같은 값으로 대체하면 안 됩니다. 손의 이전 grasp 명령 context도 센서 feedback이 아니라 한 step shift한 command history입니다.

전처리에서 정해야 하는 의미
선택변환의 의미주의할 점
Absolute / relative절대 목표 또는 현재 pose에서 목표까지의 변화회전 표현·합성 순서·현재 feedback 필요
Crop / resize원본 pixel에서 학습 시각 입력으로 변환카메라별 순서와 실제 유효 영역 확인
Progress / success진행률 또는 마지막 N step 기반 보조 label센서로 측정한 실제 성공·과제 성적과 구분
Pose / hand / gripper예측할 채널과 표현 선택모델 출력 복원 후 non-pose tail 보존
Padepisode 끝의 부족한 horizon 구간 표시실제 정답 action과 padding을 구분

Output을 추가하는 일은 체크박스 하나를 늘리는 것으로 끝나지 않았습니다. target 조립·내부 회전 표현·decoder·명령 split까지 같은 채널이 살아 있어야 합니다. Tesollo 핸드 확장에서는 이 경로의 차원·소속·명령 의미를 이어서 확인했습니다.

3.3 Model family·provider·recipe를 checkpoint까지 전달

ACT와 Diffusion은 같은 모델에서 실행 옵션만 바꾼 것이 아닙니다. 공통 학습 흐름 위에 family·provider·recipe와 각 provider 설정을 구분하고, 이를 run manifest와 checkpoint에 저장해야 합니다. 모델이 DP인데 상태·UI·auxiliary 경로는 ACT로 남는 문제도 이 경계를 따라 조사했습니다.

Checkpoint에는 weight 외에 input/output key·shape, camera_names, robot/hand 구성, action 표현과 정책 실행 설정이 필요합니다. ACT의 horizon·TE와 Diffusion의 observation/action steps·denoising 설정은 각각 다른 의미입니다. 배포 화면이 weight 파일 이름만 보고 실행 규칙을 추정하면 학습한 모델과 다른 방식으로 출력을 소비하게 됩니다.

제 Native Diffusion 확장은 학습·checkpoint·mock inference 경로를 통합한 작업입니다. 연구팀이 학습한 SCDP를 실제 로봇에서 실행한 경험과는 별도입니다. 두 경로가 공통 배포 화면에 있어도 학습 주체와 검증한 결과는 합쳐지지 않습니다.

4. 호환성과 실제 실행

4.1 학습 준비와 배포 호환성을 서로 다른 시점에 검사

학습을 시작할 수 있다는 판정은 장치에서 바로 실행할 수 있다는 판정이 아닙니다. 학습이 끝난 뒤 카메라 순서·핸드 profile·소속 로봇이 달라질 수 있기 때문입니다. Backend가 ready/warn/blocked 이유를 반환하고 UI는 그 결과를 보여주는 쪽으로 기준을 모았습니다.

4.2 관측에서 장치 명령이 되기까지의 실행 경계

Native runtime은 현재 관측을 조립해 family에 맞는 executor로 전달합니다. ACT는 chunk를 소비하거나 TE로 같은 목표 시점의 후보를 조합하고, Diffusion은 정책별 action queue로 실행 구간을 소비합니다. 모델 내부의 회전 표현은 다시 해석 가능한 action 값으로 복원한 뒤 key별로 나눕니다.

Action은 아직 SDK 명령이 아닙니다. command builder가 pose·joint·gripper·hand 명령으로 변환하고, backend가 소속 장치와 현재 제어 상태를 확인해 dispatch합니다. 예를 들어 grasp primitive와 joint target은 같은 step에서 무조건 더해 보내는 값이 아니라 서로 다른 실행 의미를 가집니다.

별도 추론 loop의 tick, 장치 수집 sample, 로봇의 servo 주기를 같은 주기로 쓰면 안 됩니다. 모델이 한 번에 여러 action을 예측하더라도 실제로 어느 구간을 언제 실행하는지는 runtime의 책임입니다. 정지도 화면 버튼의 상태 변경과 함께 loop·worker·해당 runtime이 가진 제어 route 정리로 이어져야 합니다.

5.2 확장성을 만드는 것은 값의 개수보다 계약의 일관성

로봇·손·정책을 늘릴수록 화면과 함수마다 예외를 추가하는 방식은 한계가 있었습니다. 같은 shape도 다른 장치의 값일 수 있고, 같은 6개 숫자도 절대 RPY와 상대 rotation vector처럼 전혀 다른 행동일 수 있었습니다.

그래서 확장은 차이를 지우는 작업이 아니라, 차이를 해석할 책임과 전달할 정보를 정하는 작업이었습니다. 카메라 순서·로봇 소속·표현·시간이 산출물에 남고 다음 단계가 그것을 확인해야 새 장치와 모델을 추가해도 기존 경로를 유지할 수 있었습니다.
