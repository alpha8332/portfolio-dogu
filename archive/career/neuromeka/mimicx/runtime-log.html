런타임 로그·실행 상태 진단

제어 경로의 회귀를 피하면서 로그 기록과 운영 화면의 표시 원천을 정리했습니다.

Technical Report

저장 로그는 증가하지만 UI가 시작 몇 줄에 멈춘 문제에 대해 정상 제어 baseline을 고정하고 application의 관측·기록·전달 경로를 다시 설계했습니다.

Lifecycle과 기존 snapshot을 journal에 합류하고 주요 장치 이벤트를 비동기 저장했습니다. 최종적으로 native의 저장 파일을 우선하는 전용 로그 취득 경로에 UI를 연결했습니다.

1. 장애·조사·설계 재구성

1.1 약 3일 멈춘 UI와 계속 갱신되는 저장 파일

Inference를 실행하면 UI의 Runtime Log에는 시작 시점의 몇 줄만 남고 이후 gripper 동작, pause, stop을 추적할 수 없었습니다. 반면 저장 로그에는 후속 이벤트가 늘고 있었습니다. 로봇이 움직이는 것, 파일이 갱신되는 것, 브라우저가 최신 이력을 읽는 것이 서로 다른 상태가 돼 있었습니다.

처음에는 polling, cache, status 갱신 race 등을 차례로 수정했지만 시작 두 줄에 머무는 증상이 남았습니다. 약 3일간 해결되지 않자 저장 로그와 UI가 같은 이력을 읽는지 다시 살폈습니다. 최종적으로 application event journal을 정리한 뒤 native 로그 응답은 저장된 run 파일을 우선하고 전용 로그 취득 경로로 UI에 전달하도록 바꿨습니다.

1.2 초기 가설과 수정해도 해결되지 않은 이유

검토·수정을 시도한 경계
관점조사한 문제해결로 판단하지 않은 이유
실행 측 publish첫 tick 결과가 blocking dispatch 후에 나오는 가능성저장 파일에는 후속 event가 있는 상황을 설명하지 못함
Status 취득무거운 status 처리·live 취득·JSON 변환 실패취득 빈도를 바꿔도 오래된 투영을 읽는 구조는 남음
브라우저in-flight 갱신·pending refresh·cached JS다른 source를 읽으면 재취득해도 이력이 맞지 않음
제어 mode로그 수정 후 InvalidMode 등 회귀표시 개선을 위해 제어 시작 조건까지 바꾸면 영향이 너무 큼

이 항목들은 당시 나눈 원인 후보와 수정 대상입니다. 하나의 예외나 한 번의 테스트 성공을 UI 정지의 근본 원인으로 확정하지 않았습니다. 특히 mode retry까지 수정 범위가 넓어졌을 때에는 로그를 고치는 작업이 로봇 동작 조건을 바꾸고 있다고 판단했습니다.

파일은 진행되는데 UI만 멈춘다면 이벤트를 만들지 못하는 문제와 표시 측이 다른 이력을 읽는 문제를 구분해야 합니다. 후자를 먼저 실증했어야 했습니다. 반복해서 보였던 start·run_started는 application 시작 경로에서 생성되므로 이 두 줄만으로 이후 runtime 출력의 전달까지 정상이라고 볼 수 없었습니다.

1.3 정상 제어 baseline을 고정하고 로그를 다시 설계

두 번째 구현에서는 정상 동작하던 baseline을 출발점으로 삼고 Inference 본체, adapter hardware 경로, RobotWorker, 안전 조건을 로그 때문에 바꾸지 않는 방침을 명확히 했습니다. 제어 측에 추가 RPC나 move retry를 넣지 않고 application 층에서 기존 상태를 관측합니다.

Lifecycle은 기존 API의 start·pause·resume·stop 처리 주변에서 기록하고, 장치 이벤트는 이미 publish된 inference state snapshot에서 추출했습니다. UI가 로그를 요청할 때마다 로봇에 질의하거나 관측을 위해 운전 mode를 바꾸지 않는 경계입니다.

로그 개선이 제어 회귀를 일으키면 무엇을 관측하는지도 믿기 어려워집니다. 이 판단은 단순히 변경량을 줄이는 일이 아니라 관측 대상을 유지한 채 관측 경로를 고치는 것을 위한 분리였습니다.

2. Application journal 설계

2.1 Lifecycle과 snapshot observer를 application에서 합류

Journal service는 event 목록, 중복 판정, active run 파일, observer와 writer thread를 가집니다. Shared state에는 정형화된 문자열 list만 넣고 service·lock·thread를 넣지 않습니다. Snapshot, deepcopy, JSON 응답이 service object에 얽히지 않도록 했습니다.

Observer의 기본 간격은 0.25초, 설정 하한은 0.05초입니다. 이는 snapshot을 확인하는 간격이며 제어 주기나 로그 전달의 실측 지연이 아닙니다. 모든 tick 출력을 저장하는 trace recorder 대신, 사람이 실행의 주요 변화를 따라갈 수 있는 event log로 범위를 잡았습니다.

2.2 Event와 formatter: 저장 위치가 달라도 같은 의미

불변 event의 구성
Field의미주의점

하나의 formatter로 HH:MM:SS | category | action | key=value를 만듭니다. Memory와 file이 따로 문장을 만들지 않아 같은 event의 의미가 저장 위치마다 달라지지 않습니다. 로그 행 시각은 표시용 local wall time입니다. 제어 간격을 재는 monotonic timer와 같은 것으로 다루지 않습니다.

시작 행에는 chunking mode, simulation 여부, TE 활성 설정을 넣습니다. 실행 조건의 출발점을 나중에 추적할 수 있습니다. 다만 te_enabled 설정만으로 개별 tick에 TE 후보가 갖춰져 실제 적용됐다는 사실까지 증명하지는 않습니다.

Start는 기록됐으나 run_started가 없으면 시작 호출 중 실패를 의심할 수 있습니다. 반대로 run_started만으로 명령이 장치에 도달했는지 판단할 수는 없습니다. 이벤트를 이해하기 쉬운 말로 표시할 때에도 실제로 통과한 처리 경계 이상의 의미를 부여하지 않도록 했습니다.

3. 장치 이벤트와 중복 억제

3.1 Gripper: raw·effective command·실기 결과를 구분

Policy의 gripper 값을 곧바로 open/close라고 부르면 threshold·hysteresis·force 방침·owner 해석을 통과한 후의 동작이 보이지 않습니다. 그래서 snapshot의 gripper runtime에서 effective_action을 읽어 open 또는 close의 변화를 기록했습니다. Raw/effective position, segment, arm index, matched arm을 필요한 맥락으로 덧붙입니다.

같은 owner의 effective action이 직전과 같으면 반복을 억제합니다. 연속된 close를 매번 출력하는 대신 어느 팔의 action이 open에서 close로 변했는지 추적하도록 했습니다. Identity는 segment를 우선하고 없으면 matched side나 arm index 같은 맥락을 사용합니다.

이 close 행은 runtime이 선택한 명령의 설명입니다. 물체를 잡았는지, 기계적으로 끝까지 닫혔는지, 설정 force에 도달했는지는 별도 feedback이나 관찰로 확인해야 합니다. 모델 출력 문제와 routing·장치 실행 문제를 구분하기 위한 로그로 만들었습니다.

3.2 Tesollo: grasp 상태·mode·force의 묶음을 추적

Tesollo hand는 grasp state를 release·grasp·hold의 정규 상태로 맞추고 mode ID·force와 묶어 비교합니다. 같은 owner에서 상태·mode·force가 같으면 행을 늘리지 않습니다. Force는 비교할 때 소수 셋째 자리로 반올림해 미세한 표현 차이로 이력이 채워지지 않게 합니다.

같은 grasp 상태라도 mode가 달라지면 다른 명령입니다. 좌우 손에서 같은 state가 나와도 서로 다른 owner로 남겨야 합니다. 이전 문자열과 비교하는 데서 그치지 않고 어느 장치의 어떤 상태가 변했는지를 signature에 담았습니다.

여기 기록하는 force는 command의 설정값입니다. 센서로 측정한 힘으로 바꾸어 읽지 않습니다. Mode가 음수로 불명확할 때 유효한 mode처럼 표시하지 않는 것도 로그에서 잘못된 상태를 추론하지 않도록 한 처리입니다.

3.3 오래된 snapshot과 반복 error를 새 사건으로 만들지 않기

Run을 바꿔도 shared state의 last_output이 직전 run의 값으로 남을 수 있습니다. Begin run에서 그 출력 timestamp를 기억하고 이보다 새로운 출력이 오기 전에는 command 유래 장치 이벤트를 억제했습니다. 새 run에 오래된 grasp나 close가 섞이지 않도록 하기 위해서입니다.

같은 error message나 완료 조건도 snapshot을 읽을 때마다 반복될 수 있습니다. Warning/error·completed는 token으로, 장치는 owner별 직전 signature로 중복을 억제합니다. 명시적인 lifecycle 조작과 반복 관측하는 state에 같은 처리를 기계적으로 적용하지 않았습니다.

Observer가 읽는 사이 여러 번 변한 뒤 원래 상태로 돌아오면 중간 상태를 snapshot만으로 복원할 수 없습니다. 이 journal은 주요 이벤트의 가독성에 집중한 관측이며 모든 command를 빠짐없이 기록하는 감사 이력은 아닙니다.

4. 저장·전달·run 분리

4.1 Async writer: 로그 I/O를 제어 판단에서 분리

Append에서는 lock 안에서 event를 memory에 추가하고 표시용 list를 갱신합니다. 기본 memory 보관량은 최신 200 event입니다. 이후 run 파일 path와 event의 묶음을 queue에 넘기고 writer thread가 UTF-8 한 행을 추기합니다. File open/write를 event 생성 lock 안에서 매번 실행하지 않는 구조입니다.

Writer는 쓰기 예외를 잡아 writer_error로 남기고 queue item의 처리 종료를 알립니다. Disk full이어도 이미 만든 memory event를 지우거나 로그 실패 때문에 move를 retry하지 않습니다. 다만 실패 행의 자동 재전송 구현은 아니므로 memory 보존과 파일 완전성은 구분해야 합니다.

Memory의 200건 상한은 queue 상한이 아닙니다. 현재 queue는 unbounded이므로 writer가 장시간 따라오지 못할 때의 backpressure까지 구현했다고 할 수는 없습니다. 주요 변화만 event화하는 설계와 queue 부하를 다루는 설계는 구분할 필요가 있습니다.

4.2 최종 수정: 저장된 이력을 우선해 UI에 반환

Memory와 file에 같은 formatter를 써도 UI가 다른 state projection을 읽으면 내용이 맞지 않았습니다. 최종 수정에서는 /api/infer/log를 만들고 native 실행 응답에서 active run 파일의 저장된 행을 먼저 읽도록 했습니다. UI는 status와 log 그리기를 분리하고 이 경로로 행을 갱신합니다.

현재 로그 응답의 우선순위
조건반환 이력해석
External runtime의 log가 존재외부 runtime status 또는 해당 state lognative journal과 다른 실행 owner
Native 저장 파일이 비어 있지 않음active run의 persisted lines실제로 저장된 이력 우선
저장 행이 아직 없음journal rendered memory, 마지막으로 state line시작 직후·file 미생성 시 fallback

Journal 내부 render_lines에는 memory와 저장 행 길이를 비교하는 경로도 있습니다. 하지만 API는 비어 있지 않은 저장 행을 먼저 반환합니다. 따라서 항상 긴 쪽이 UI에 오는 것은 아닙니다. Async writer가 밀려 파일이 중간까지 저장됐다면 UI도 그 저장 범위를 보여줄 수 있습니다.

저장 파일을 우선하는 방침은 UI와 남아 있는 실행 기록을 대조하기 위한 것입니다. 엄격한 즉시 동기화나 무결손 보장으로 설명하지 않습니다. 최종적으로 후속 이벤트가 UI에 표시되는 것을 실행 시 확인하고 수정 사항을 merge했습니다.

4.3 UI 취득 분리와 외부 모델의 로그 소유권

브라우저에서는 Runtime status를 적용할 때 log 재그리기를 억제하고 로그 refresh를 독립시켰습니다. 전용 in-flight flag로 중복 request를 억제하며 fetch에 no-store를 지정합니다. 행은 textContent로 표시해 이전의 무거운 status 응답이 로그를 오래된 내용으로 덮어쓰는 경로를 피했습니다.

현재 UI는 외부 모델 runtime의 status log를 먼저 시도하고 이용할 행이 없으면 native log API로 진행합니다. SCDP 같은 외부 worker의 실행 이력을 native journal snapshot에 억지로 섞지 않기 위해서입니다. Native 문제의 해결을 설명할 때에도 이 별도 owner를 구분해야 합니다.

전용 endpoint만 만들면 모든 표시 문제가 해결되는 것은 아닙니다. 어떤 run path를 읽는지, 응답 끝이 파일과 같은지, UI가 다른 status 응답으로 덮어쓰는지를 순서대로 비교합니다. 이 문제에서는 비교 대상을 고정한 것이 polling 횟수 조정보다 유효했습니다.

4.4 Run 전환·writer 장애·종료 처리

Begin run에서는 microsecond를 포함한 run명으로 active file을 바꾸고 memory·중복 token·장치의 직전 상태를 초기화합니다. Queue item에 enqueue 당시 path가 담겨 새 run이 시작돼도 이전의 대기 event가 새 파일에 쓰이지 않도록 했습니다.

Shutdown에서는 observer에 정지를 알리고 writer에 sentinel을 전달한 뒤 join합니다. Join에 시간 상한이 있으므로 무제한 기다려 반드시 모든 행을 flush하는 구조는 아닙니다. 파일 저장·앱 종료·제어 정지의 책임을 혼동하지 않고 남은 파일을 실행 이력의 확인 대상으로 다룹니다.

실행 중 UI 로그와 저장 파일에 후속 이벤트가 함께 증가하는 것을 확인한 뒤 merge했습니다. 자동 fixture에서는 행 내용·순서, 오래된 snapshot의 분리, 중복 억제, writer 실패 시 memory 보존을 나눠 검사하도록 했습니다. UI의 한 번의 갱신과 journal의 내부 일관성을 서로 다른 검증 대상으로 다뤘습니다.

수용 조건은 단순히 행이 보이는 데 있지 않습니다. Control baseline을 유지하면서 같은 run의 후속 event를 파일·API·UI에서 추적할 수 있어야 합니다. 제어 정상과 표시 정상은 각각 확인해야 했습니다.

5.2 Engineering Note: 관측의 정확성은 source와 경계에서 결정

이 문제로 가장 달라진 것은 로그가 안 보일 때 먼저 묻는 순서입니다. 이전에는 언제 publish되는지, 몇 번 poll하는지부터 추적했습니다. 하지만 저장 측에는 이미 답이 있었습니다. 어떤 source를 어떤 run으로 누가 읽는지 맞추지 않으면 표시를 반복해서 수정해도 같은 증상으로 돌아옵니다.

관측을 위해 제어 측에 처리를 더하면 로그를 고치다가 원래 로봇 동작을 깨뜨릴 수 있습니다. 정상 baseline을 고정하고 기존 snapshot으로 관측을 옮긴 뒤에야 제어와 로그 각각의 문제를 검증할 수 있었습니다.

단일 formatter, file 우선, 전용 endpoint는 역할이 다릅니다. Formatter는 한 행의 의미를, source 통일은 이력을 맞추고, UI 취득 분리는 오래된 응답의 덮어쓰기를 피합니다. 특정 구조의 이름을 도입하는 것에 그치지 않고 의미·저장·전달의 각 경계가 무엇을 보장하는지 설명할 수 있어야 한다고 이해했습니다.
