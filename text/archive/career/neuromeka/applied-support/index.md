## 1. 지원 맥락과 기술적 접점

### 1.1 기능을 적용할 환경과 전달 대상을 맞추는 지원

플랫폼 기능을 만드는 일과 다른 과제에서 사용할 수 있도록 준비하는 일은 연결돼 있었습니다. 두 대의 Indy12를 함께 운영할 때는 구성원이 같은 로봇·장치·데이터를 선택하도록 절차를 정리했고, 기업·연구 지원에서는 구동 조건과 모델 출력의 의미를 맞추었습니다.

지원 대상마다 다른 기술적 연결점
| 업무 | 연결해야 했던 것 | 남긴 결과

| 한전 과제 적용 준비 | 독립 로봇·EE·입력 장치·session·capture·training | 내부 운영 매뉴얼과 단계별 점검 기준

| 삼성SDI 실행 준비 | 로봇 구동 상태·수동/자동 mode·Vive runtime·양팔 API | 실행 순서와 최소 경로 확인 절차

| KAIST 연구 협업 | 카메라·관절 정보, 학습 모델 IO와 로봇 명령 | 정보 전달과 출력 변환 adapter·실물 실행 확인

이 범주에서는 적용 준비와 기술 전달을 설명합니다. 데이터 수집 task의 관찰은 Experiments에, 다중 로봇·외부 모델의 공통 구현은 MiMicX 보고서에 연결해 각 업무의 책임과 설명 수준을 구분했습니다.

### 1.2 운영자가 재현할 수 있도록 상태를 설명

한전 과제용 매뉴얼은 로봇을 두 번 등록하는 순서에서 끝나지 않았습니다. 세션의 두 participant, 각 로봇의 엔드이펙터, 입력 장치와 calibration, task별 capture plan이 서로 같은 구성을 가리키도록 정리했습니다. 수집 후에는 저장한 episode를 검사하고 Replay·학습 준비로 이어지게 했습니다.

### 1.3 상대가 전달한 모델과 기존 로봇 플랫폼의 접점

외부 학습 결과물은 파일을 load하는 것만으로 로봇에 연결되지 않았습니다. 실제 checkpoint는 16차원인데 wrapper는 이전 22차원을 전제한 경우가 있었고, 회전벡터의 상대 변화량을 기존 API의 절대 RPY 각도로 전달하면 뜻이 달라졌습니다. 모델을 재학습하는 대신 adapter에서 이 계약을 맞추었습니다.

## 2. 전달 방법과 Engineering Note

### 2.1 정상 관찰과 실패 지점을 함께 전달

운영·협업 문서에 남긴 질문
| 단계 | 독자가 확인해야 할 것

| 준비 | 누가 어떤 로봇·장치·모델을 사용할 것인가

| 시작 | 등록·연결·제어 mode·입력 유효성이 충족됐는가

| 실행 | 명령의 소유자·단위·좌표 표현이 맞는가

| 기록 | raw·영상·선택 episode와 설정의 대응이 남았는가

| 복구 | 어느 경계까지 정상이었고 무엇이 달라졌는가

사용자가 보는 등록 표시와 실제 장치 응답, 모델의 출력값과 발행된 명령, 기록 중지와 episode 저장은 서로 다른 사건입니다. 다음 사람이 같은 문제를 확인할 수 있도록 현재 상태와 예상 결과를 짝으로 남겼습니다.

### 2.2 Engineering Note

설정을 넘겨주는 것만으로 같은 동작이 재현되지는 않았습니다. 같은 모델 이름도 실제 파일과 출력 계약이 다를 수 있었고, 화면에서 선택한 한 로봇이 세션 전체를 뜻하지도 않았습니다. 기술 전달의 단위는 파일이나 클릭 순서가 아니라, 그 정보가 성립하는 조건과 확인 방법이어야 한다는 점을 배웠습니다.
