## 1. 시험 대상과 판정 기준

### 1.1 약 1,200개 항목을 실제 장비에서 검증

Framework 신규 기능과 사용자 기능을 CB4.0·IndyKey·NURI·Conty의 통합 환경에서 검사했습니다. 약 1,200개 규모의 항목을 약 2~3주 동안 담당하면서 화면 표시뿐 아니라 설정·입력 신호와 실제 동작이 정상 결과와 맞는지 확인했습니다.

발견한 문제는 항목·환경·기대 결과·실제 관찰을 묶어 전달했습니다. 제품 코드 수정과 최종 릴리즈 판단은 담당자의 영역이며, 제 업무는 검사 수행과 재현·기록·전달을 통해 조치할 대상을 분명히 하는 일이었습니다.

### 1.2 제품 버전·상태·주변 장비를 시험 조건으로

시험 전제와 역할
| 대상 | 검사에서 확인한 관계

| Framework / Conty | 화면의 설정·프로그램 의도가 controller 동작으로 이어지는가

| CB4.0 | 입출력·제어 상태·연결 장비의 동작이 표시와 일치하는가

| IndyKey | 제어 mode·실행·일시정지·복구 상태가 실제 로봇과 맞는가

| NURI | pose·motion·end-tool·servo 상태의 실제 관찰

| 주변 장비 | 지그·센서·케이블·외부 입력 등 항목별 선행 조건

같은 메뉴라도 robot mode·servo·로그인 상태와 연결 장비가 다르면 시험 조건이 달라집니다. 실행이 안 된다는 결과를 바로 제품 결함으로 기록하기 전에, 해당 항목이 전제한 환경이 갖추어졌는지 확인했습니다.

### 1.3 항목을 사전 조건·절차·정상 관찰로 읽기

한 항목을 해석하는 순서
| 구성 | 질문

| 화면·탭/영역·기능 | 어느 기능의 어떤 상태를 검사하는가

| 테스트 내용 | 등록·조회·수정·실행 중 무엇을 확인하는가

| 추가 준비물·적용 장비 | 실제로 수행 가능한 조건인가

| 테스트 절차 | 설정·적용·실행 순서가 빠지지 않았는가

| 정상 결과 | 어떤 값·메시지·신호·동작을 보아야 하는가

| 관찰·판정·비고 | 실제로 무엇이 달랐고 어떤 조치가 필요한가

“정상 동작”이라는 문장만으로는 판정하기 어려웠습니다. 예를 들어 신호 설정 항목에서는 값이 화면에 저장되는 것과 실제 출력이 바뀌는 것이 다른 확인입니다. 프로그램 명령에서도 설정값을 바꾸는 일과 명령 이후 동작에 적용되는 일을 나누어 보았습니다.

테스트는 시작 상태에서 조작을 가했을 때 기대한 상태나 출력으로 전환되는지 비교하는 일입니다. 시작 상태가 다르거나 관찰 대상이 모호하면 같은 기능에도 서로 다른 판정을 내릴 수 있습니다. 그래서 준비 조건, 수행 단계, 확인할 결과가 하나의 항목 안에서 연결되는지부터 살폈습니다.

### 1.4 검사에서 다룬 기능 영역

기능 영역과 판정 대상
| 영역 | 확인한 기술 관계

| 화면·프로그램·실행 | 진입·선택·상태 표시와 실제 실행/정지

| 툴·참조좌표계·환경 | 저장된 설정과 선택·적용 대상

| Gain / motion | 설정한 명령·제어 mode와 이후 동작

| I/O / Modbus | server·variable·신호 설정과 입력/출력 관찰

| 센서·엔드툴 | 실제 연결·모델 선택·지그 반응

| 한계·오류·복구 | 설정의 반영·오류 표시·복구 후 상태

설정 화면에서 값을 입력하는 기능과 프로그램이 실행 중 그 값을 사용하는 기능은 같은 항목이 아니었습니다. 이 차이를 이해해야 어디까지 정상인지, 기대 결과를 어떤 관찰로 써야 하는지 구체적으로 전달할 수 있었습니다.

## 2. 문제 분리와 시험서 개선

### 2.1 시트 번호와 UI 번호가 달랐을 때

메모에는 시트의 87번과 UI의 76번, 시트의 152번과 UI의 140번처럼 번호가 다른 사례가 남아 있습니다. 항목 추가·제외·순서 변화가 있는 상태에서 번호만 맞추면 다른 기능을 검사할 수 있어, 화면·탭·기능과 테스트 내용을 함께 비교했습니다.

지속적으로 같은 항목을 추적하려면 파일 버전과 실제 행, UI 위치를 묶어야 합니다. 당시 도구의 UI index는 실제 Excel 행 목록을 따라가므로 단순히 index에 일정 값을 더하는 방식으로 모든 버전을 대응시킬 수는 없었습니다.

엔드툴 지그가 없거나 힘·토크 센서 케이블이 NURI 포트와 맞지 않는 경우에는 준비 조건을 기록했습니다. 용접기 같은 선행 장비, 보류된 항목, 다른 담당 범위도 분리했습니다. 이런 항목을 실제 동작 실패와 같은 오류로 세면 제품 상태를 잘못 전달하게 됩니다.

### 2.3 실제 메뉴에 맞게 시험 경로와 전제를 교정

시험서에서 구체화한 수정
| 이전 문제 | 수정 방향 | 판정에 미치는 의미

| Gain tuning의 메뉴 경로·진입 전제 부족 | 해당 gain 탭과 필요한 로그인 전제 명시 | 다른 탭에서 잘못된 조건으로 검사하지 않음

| 환경 저장을 “저장”으로만 지시 | “다른 이름 저장”과 환경 객체 이름 구분 | 기존 객체 갱신과 새 객체 생성 구별

| Modbus 설정 절차의 누락 | server 생성·transport·variable 연결을 나누어 설명 | server 등록과 실제 신호 동작을 분리

| 명령어·용어 혼동 | Sphere/Wall, Annotation/Alarm 등 정정 | 다른 기능과 관찰 대상을 혼동하지 않음

수정은 맞춤법만 다듬는 일이 아니었습니다. 실행 전제가 빠지면 검사 자체가 다른 조건에서 수행됩니다. 실제 화면에서 어느 단계가 필요한지 확인하고 다음 검사자가 같은 경로로 진입할 수 있도록 수정 지점을 남겼습니다.

Modbus RTU 항목은 server를 하나 추가하는 것으로 끝나지 않았습니다. RTU 타입과 transport를 지정하는 단계, 프로그램 variable에 해당 server·주소·신호를 연결하는 단계, 사용 중인 server 삭제 시 확인 메시지를 보는 단계가 서로 달랐습니다. 통신 설정 객체의 생성과 프로그램에서 그 객체를 참조하는 상태를 분리해 절차를 정리했습니다.

### 2.4 정상 결과를 메시지·값·상태로 구체화

servo 상태를 막연히 “상태코드”로 쓰는 대신 off/on 이후 표시되는 단계와 유지 상태를 구분하고, empty 항목·위치 미등록 메시지·삭제 확인 팝업 등 실제로 보아야 할 결과를 추가했습니다. 수치 항목에서는 입력한 설정과 표시값의 관계도 다시 읽었습니다.

툴 제원·질량 중심·관성 입력에서도 값을 저장한 화면과 그 제원을 선택해 사용하는 명령을 구별해야 했습니다. 설정이 화면에 남았다는 사실만으로 동작에 적용됐다고 결론 내리지 않고, 해당 항목의 목적에 맞는 결과를 확인하도록 정리했습니다.

관찰을 명확하게 바꾼 사례
| 대상 | 구체화한 확인 | 왜 필요한가

| Servo 상태 | Off 이후 Ready Switch, On 이후 SWITCHED_ON을 거쳐 OPERATION_ENABLED 유지 | 명령을 누른 사실과 최종 운전 가능 상태를 구별

| SetToolMass | 직접 입력과 저장된 툴 제원 불러오기를 구분하고 질량·질량 중심·관성모멘트의 입력 경로 명시 | 서로 다른 설정 경로를 같은 절차로 검사하지 않음

| 프로그램 설정 명령 | 해당 명령 이후의 동작에 설정이 반영되는지 관찰 | 전역 저장값과 프로그램 실행 시점의 효과를 구별

| 환경 저장 | Save As와 env 객체 이름을 사용해 새 환경 생성 확인 | 툴 설정을 복사한 잘못된 기대 결과를 바로잡음

특히 서보 상태에서는 순간적으로 지나가는 상태와 계속 유지되어야 하는 상태가 다릅니다. “상태코드 확인”을 상태 전이와 유지 조건으로 풀어 써야 검사자가 어느 순간의 표시를 정상으로 볼지 일치시킬 수 있었습니다.

## 3. 실제 이상·상태·전달

### 3.1 실제 동작 이상과 문서 교정을 별도로 전달

중앙 감속 제어가 동작하지 않는 현상과 안전 설정 파일을 저장할 때 permission denied가 발생하는 사례를 기록했습니다. 메뉴명 수정이나 장비 미준비와는 다른 제품·환경 동작의 이상이므로 재현 조건과 실제 결과를 따로 전달했습니다.

정상 기대·실제 관찰·발생 조건과 이후 확인이 필요한 부분을 묶어야 담당자가 수정할 대상을 정할 수 있었습니다. 예를 들어 permission denied는 파일 저장 단계에서 관찰한 증상입니다. 설정값의 의미가 틀린 문제인지, 파일 접근 경로·권한의 문제인지 조사할 수 있도록 값 입력과 저장 동작을 구별해 전달해야 했습니다.

### 3.2 위험 동작에서는 상태와 복구 조건도 기록

브레이크 해제·직접교시·충돌 감지·한계값 시험은 단순 UI 조작 이상의 상태 변화가 있습니다. 로봇의 현재 mode·servo·중력에 따른 움직임과 오류 뒤 복구 상태를 함께 고려해야 했습니다. 당시 운영 메모에 실행 조건과 주의점, 복구 뒤 관찰을 남겼습니다.

검사 기록에는 어느 상태에서 어떤 결과를 관찰했는지가 필요합니다. 다른 장비의 버튼 조합이나 세부 조작을 그대로 복사하기보다 시험 환경과 책임 범위를 명확히 하고, 안전 관련 시험을 일반 기능의 단순 성공/실패로 축소하지 않았습니다.

### 3.3 담당자가 다시 확인할 수 있는 문제 전달

전달할 정보의 연결
| 필드 | 역할

| 시험서 버전·항목과 화면 위치 | 같은 대상에 다시 도달

| 제품·연결 장비·mode·선행 설정 | 재현 조건 복원

| 수행 단계 | 어느 전환에서 달라졌는지 구분

| 정상 기대와 실제 관찰 | 조치할 차이 명시

| 미진행·보류·문서 교정·제품 이상 | 필요한 후속 조치 구분

| 조치와 재확인 결과 | 전달·수정·재검사를 서로 다른 상태로 관리

제품 수정은 담당 개발자의 일이고 저는 재현·기록·전달을 맡았습니다. 문제를 넘긴 상태, 담당자가 조치한 상태, 수정본으로 재확인한 상태는 각각 다릅니다. 재검사는 같은 항목과 환경으로 돌아가 기대 결과를 다시 비교하고, 수정 전 관찰과 연결할 수 있어야 합니다.

## 4. 기록과 Engineering Note

### 4.1 많은 항목을 같은 방식으로 읽고 기록

약 1,200개 규모의 시트에는 한 기능의 등록·수정·삭제·조회·동작과 여러 조건이 나누어 들어 있습니다. 시트 행 수와 고유 기능 수, 테스트한 장비 조합 수를 같은 숫자로 보지 않았습니다. 실제로 실행할 수 없는 항목의 이유도 남겨야 수행 범위를 이해할 수 있습니다.

시트를 계속 넘기며 항목과 결과를 맞추는 부담을 줄이기 위해 검사 기록 Web UI를 개발했습니다. 다른 팀원과도 같은 방식으로 항목을 읽고 판정을 남겼지만, 제품 검사는 계속 사람이 실제 장비에서 수행했습니다.

### 4.2 Engineering Note

검사 결과가 다르게 나왔다고 모두 제품 결함은 아니었습니다. 경로가 틀린 시험서, 없는 지그, 잘못 연결된 신호와 실제 동작 이상은 다음 조치가 달랐습니다. 판정 전에 실패의 종류와 성립 조건을 분리해야 검증 결과가 기술적인 정보가 된다는 점을 배웠습니다.

또한 정상 결과를 명확히 쓰는 일은 기능을 이해하는 과정이었습니다. 화면의 저장과 실제 적용, mode 전환과 로봇 동작을 구별해 설명할 수 있어야 다른 검사자와 같은 기준을 공유할 수 있었습니다.
