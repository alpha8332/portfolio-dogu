## 1. 목적·구조·Excel 읽기

### 1.1 검사자가 실제로 수행하는 흐름 위에 만든 도구

Excel 검사서를 읽고 실제 장비를 시험한 뒤, 판정과 사유를 다시 같은 행에 기록해야 했습니다. 이 흐름을 브라우저의 항목 단위 화면으로 연결하는 팀용 도구를 FastAPI·openpyxl·HTML/CSS/JavaScript로 처음부터 개발했습니다.

AI가 코드 수정안을 제안했고, 저는 실제 화면·선택값·Excel 결과에서 달라진 점을 다시 설명하며 요구와 구현을 교정했습니다. 테스트 항목의 자동 로봇 제어보다 사람이 읽고 판정한 기록을 정확한 행에 보존하는 것이 이 도구의 목적이었습니다.

브라우저는 loaded·total·index와 현재 입력을 관리하고 API로 항목 조회·판정을 요청합니다. backend의 ReleaseState는 load한 workbook·active sheet·header mapping·실제 행 목록·분류 값을 보유하고, openpyxl이 별도 결과 사본에 기록합니다.

process-global STATE 하나와 lock을 사용한 구조입니다. lock은 동시에 workbook을 수정하는 경계를 보호하지만 검사자마다 다른 workbook과 현재 세션을 격리하는 기능은 아닙니다. 팀이 함께 사용한 경험과 독립 동시 세션 지원은 구분해야 했습니다.

### 1.3 헤더 탐색과 실제 case 행 선별

active sheet의 앞 120행 이내에서 화면·탭/영역·기능·테스트 내용·테스트 절차·정상 결과가 모두 있는 행을 찾았습니다. 고정된 첫 행만 읽으면 위쪽 안내·병합 제목이 있는 시트를 처리하기 어렵기 때문입니다.

헤더 아래에서는 기능·테스트 내용·절차·정상 결과 중 하나라도 값이 있는 행을 case로 선별하고, 서식만 남은 빈 행은 건너뛰었습니다. 화면·탭·기능은 앞의 값을 이어 읽어 표시하고 절차는 줄 단위 목록으로 풀었습니다. 표시용 forward-fill은 원본 병합 구조를 전부 해제하는 작업과 다릅니다.

UI의 현재 번호는 data_rows[index]로 실제 Excel 행에 연결합니다. 빈 행과 상위 제목이 섞여 있으므로 index에 고정 offset을 더해 기록하지 않았습니다. 이전·다음 이동도 이 목록의 범위 안에서 처리했습니다.

시트 버전에 따라 선택되는 행의 수와 순서가 달라집니다. 화면에 보이는 1번을 제품 전체의 영구 case ID로 해석할 수는 없으며, 다음 버전에서도 같은 항목을 추적하려면 버전과 항목 식별을 함께 보존해야 합니다.

## 2. 항목 실행과 기록

### 2.1 원본을 보존하고 결과 사본을 생성

파일 목록에서 data 폴더의 XLSX를 선택하고 검사자 이름을 입력한 뒤 load합니다. backend는 workbook을 읽어 헤더와 행을 찾고 timestamp가 붙은 결과 파일을 별도 output 폴더에 저장한 다음, 그 사본을 다시 열어 현재 STATE로 관리했습니다.

이후 판정은 원본이 아닌 결과 사본에 기록됩니다. 파일명 timestamp는 산출물을 구별하는 수단이며, 충돌 없는 다중 사용자 저장이나 불변 감사 이력을 보장하는 설계로 보지는 않았습니다.

### 2.2 한 항목을 읽고 다음 판정으로 이동

항목 응답에는 분류·테스트 내용·절차·정상 결과와 현재 판정·기록 시각·펜던트 선택·오류 사유를 담았습니다. 화면은 그 값을 표시하고 index와 total을 기준으로 이전·다음 버튼을 제어합니다. 기록을 다시 읽어 왔을 때 선택 상태와 사유도 해당 항목에 맞게 복원하도록 했습니다.

통과·오류 저장 요청이 성공한 뒤에는 다음 항목으로 이동합니다. 마지막 항목에서는 범위를 벗어나지 않게 했습니다. 저장 성공 응답과 화면 이동을 연결해야 판정이 파일에 남지 않은 채 다음 항목을 진행하는 혼동을 줄일 수 있었습니다.

### 2.3 적용 장비의 O와 실제 검사 조건을 분리

초기에는 시작 화면에서 선택한 장비 옵션을 전체 행에 O로 표시하는 방식이 있었습니다. 그러나 기준 시트의 장비 적용 여부와 이번 항목에서 실제 사용한 장비는 뜻이 다릅니다. 한 번의 선택이 모든 행의 의미를 바꾸는 구조를 제거하고, 유선 펜던트는 case별로 선택해 해당 행에만 기록하도록 바꾸었습니다.

선택지는 인디키·nPad·없음이고, 체크박스 형태이지만 한 항목에서 하나만 선택하도록 처리했습니다. 단순히 UI 모양을 바꾼 일이 아니라 적용 범위의 메타데이터와 실제 수행 조건을 분리한 변경이었습니다.

검사자는 별도의 문제였습니다. 현재 구현은 검사자 이름을 각 case 행이 아닌 workbook 상단의 공통 셀에 기록합니다. 검사자가 바뀌면 그 셀을 갱신하므로, 각 항목을 누가 판정했는지의 이력까지 보존하려면 행별 검사자나 별도 판정 이력이 필요합니다. 팀 공동 사용과 개별 판정의 책임 추적을 같은 기능으로 보아서는 안 됐습니다.

Pass 요청은 검사자·펜던트를, Fail 요청은 여기에 오류 사유를 포함합니다. backend는 load 상태와 index 범위를 확인하고 실제 행을 찾은 뒤 결과·기록 시각·검사자·펜던트 선택을 기록하고 workbook을 저장합니다. 오류일 때는 비고에 오류 사유도 씁니다.

오류 사유가 비어 있으면 frontend에서 입력을 요구하도록 했습니다. 결과를 저장한 뒤에는 갱신된 항목을 반환해 화면과 파일이 같은 값을 읽는지 확인하는 흐름으로 연결했습니다.

## 3. 문제해결과 저장 계약

### 3.1 오류 판정에서만 선택값이 빠진 문제

통과에서는 펜던트가 저장되는데 오류에서는 저장되지 않는 문제가 있었습니다. frontend가 wired_pendant를 보내더라도 Fail route가 저장 함수로 그 인자를 넘기지 않으면 해당 값이 빠집니다. 요청 모델·route·저장 함수의 전달 경로를 함께 맞춰야 했습니다.

Pass와 Fail이 비슷하게 보인다는 이유로 한쪽만 확인해서는 충분하지 않았습니다. 선택→판정→Excel 행→다시 항목 조회의 경로를 양쪽에서 비교하는 것이 이 오류를 조사하는 기준이 됐습니다.

### 3.2 없는 버튼 때문에 파일 목록 초기화가 멈춤

화면에서 버튼을 제거한 뒤 Excel 파일 목록이 나타나지 않는 문제가 있었습니다. 파일이 사라진 것이 아니라, 없는 DOM 요소에 이벤트나 disabled 상태를 설정하다 JavaScript가 중단돼 뒤의 목록 초기화가 실행되지 않는 경로를 살폈습니다.

이벤트 연결·상태 변경 전에 요소가 존재하는지 검사하고, 초기화는 DOMContentLoaded 뒤에 수행하도록 보완했습니다. 서버 목록 응답과 화면의 JavaScript 실행을 나누어 확인해야 파일 읽기 문제로 오인하지 않을 수 있었습니다.

선택 기능이 없는 화면을 허용하는 guard와 필수 기능의 실패를 조용히 숨기는 처리는 다릅니다. 파일 목록 오류를 catch한 뒤 아무 표시도 하지 않는 부분은 개선할 지점으로 남았습니다.

### 3.3 기록 시각·선택·판정·사유를 나누어 배치

기록 시각과 유선 펜던트, 판정 버튼과 오류 내용이 한 줄에 몰리자 현재 선택과 다음 행동을 확인하기 어려웠습니다. 기존 화면을 기준으로 기록 메타정보, 통과/오류 버튼, 오류 사유를 나누어 배치하고 두 판정 버튼의 크기를 맞추도록 요구했습니다.

또한 수정 후 화면이 그대로 보일 때는 브라우저 캐시와 서버의 실제 코드 반영을 따로 확인했습니다. 화면 반영 문제와 Fail 저장 인자 누락을 같은 원인으로 다루지 않았습니다. UI와 backend의 실패 지점을 나누어 보는 작업이었습니다.

### 3.4 읽기 헤더가 유연해도 쓰기 열은 고정돼 있었음

시트 버전과 저장 위치의 관계
| 대상 | 초기 형식 | 열이 추가된 후속 형식

| 결과 / 기록 시각 | V / W | W / X

| 검사자 메타 위치 | W3 계열 | X3 계열

| 비고 | X열 계열 | Y열 계열

| 내용 읽기 | 필수 헤더명 탐색 | 같은 내용 헤더명 유지

| 남은 충돌 | 고정 V/W writer | 후속 시트의 다른 의미 열에 기록될 수 있음

내용 헤더를 찾아 읽는 부분과 판정 결과를 쓰는 부분은 서로 다른 계약이었습니다. 코드에는 결과·시간을 V/W 고정 열로 다루는 부분과 시작 검사자를 X3에 기록하지만 조회·판정에서는 W3를 사용하는 부분이 함께 남았습니다. 한 셀만 옮기면 읽기·갱신까지 함께 바뀌는 것은 아니었습니다.

시트가 바뀌면 결과·시간·비고·검사자 위치를 한 schema로 정의하고 load·read·write가 같은 정의를 사용해야 합니다. 인턴 기간에 남긴 단계에서는 이런 위치의 일관화가 후속 개선 과제였습니다.

### 3.5 선택 해제·판정 변경과 이력의 보존

펜던트 선택값이 비어 있으면 저장 함수가 해당 갱신을 건너뛰는 구조여서 화면에서 체크를 해제했다고 이전 O가 반드시 지워지는 것은 아니었습니다. Pass에서는 기존 오류 비고를 지우지 않으므로, 오류에서 통과로 바꿀 때 어떤 사유를 남길지도 별도 규칙이 필요합니다.

현재 행의 결과와 시각을 갱신하는 기능은 판정 변경마다 별도의 불변 이력을 쌓는 기능과 다릅니다. 최신 판정, 이전 오류, 조치와 재검사를 구분해 저장하려면 history 구조와 화면의 변경 의미를 함께 설계해야 했습니다.

## 4. 산출물과 Engineering Note

### 4.1 생성 파일과 실제 UI 내보내기를 구분

backend에는 현재 workbook을 저장해 결과 파일을 반환하는 export 경로가 있습니다. 반면 보존한 HTML에는 다운로드 버튼이 없고 JavaScript는 해당 요소가 없으면 연결을 건너뛰도록 되어 있습니다. API가 존재하는 것과 사용자가 화면에서 끝까지 내보낼 수 있는 것은 다른 확인입니다.

개발 중 결과 사본과 일부 표본 판정이 남아 있지만, 모든 파일이 전체 검사 완료 원장은 아닙니다. 한 결과 사본은 시작 검사자 셀만 바뀐 상태였습니다. 저장·생성 경로의 확인과 실제 제품 QA의 전체 수행 결과를 구분했습니다.

### 4.2 직접 개발·검증과 팀 공동 사용

항목 읽기·탐색·판정·사유와 장비 조건 기록을 연결한 팀용 도구를 만들고 실제 검사에서 다른 팀원과 함께 사용했습니다. AI 수정안을 받은 뒤에도 화면이 바뀌지 않거나 저장이 빠진 현상을 다시 설명하며 요구를 좁히고 실제 파일을 대조했습니다.
