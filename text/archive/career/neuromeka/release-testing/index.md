## 1. 제품 검증과 기록 도구

### 1.1 실제 장비의 검증과 검사 기록 도구 개발

CB4.0·IndyKey·NURI·Conty가 연결된 환경에서 약 1,200개 규모의 릴리즈 테스트 항목을 약 2~3주 동안 담당했습니다. 기대 결과와 실제 표시·설정·신호·동작을 비교하고, 절차의 문제와 제품 동작 이상을 구분해 담당 개발자에게 전달했습니다.

동시에 방대한 Excel 항목을 순서대로 읽고 판정·사유를 남길 수 있는 Web UI를 처음부터 개발했습니다. AI의 코드 제안을 실제 화면과 저장 파일에 대조해 수정했고, 다른 팀원과 실제 검사에서 함께 사용했습니다. 사람이 하는 제품 검사와 그 기록을 돕는 소프트웨어는 서로 다른 책임으로 나누었습니다.

### 1.2 제품 릴리즈 QA — 무엇을 정상으로 볼 것인가

검사의 출발점은 기능 이름이 아니라 사전 조건·절차·정상 결과였습니다. 지그나 케이블이 없어 실행하지 못한 항목, 메뉴 경로가 틀린 시험서, 실제 제품 동작 이상은 필요한 조치가 달랐습니다. 번호가 맞지 않는 경우에도 시트와 화면의 기능 내용을 먼저 대조했습니다.

### 1.3 릴리즈 검사 Web UI — 검사 의미를 잃지 않고 저장

FastAPI·openpyxl과 HTML/CSS/JavaScript로 파일 선택, 항목 표시·이동, 통과·오류와 사유 입력, 결과 사본 저장을 연결했습니다. 기준 시트의 장비 적용 표시와 실제 그 항목에서 사용한 펜던트 선택을 구별하고, 읽기·요청·저장·다시 표시의 경로가 이어지도록 다뤘습니다.

## 2. 결과와 Engineering Note

### 2.1 검사·기록·제품 수정의 결과를 구분

결과와 책임의 관계
| 활동 | 내가 남긴 것 | 후속 판단

| 제품 검사 | 기대·실제 결과, 재현 조건과 미진행 사유 | 담당 개발자의 조치와 재검사 대상

| 시험서 교정 | 메뉴 경로·사전 조건·용어·정상 결과의 수정 지점 | 다음 검사자가 같은 기준으로 수행

| 기록 도구 개발 | 항목 탐색·판정·사유·시간·장비 선택의 저장 경로 | 시트 버전과 저장 계약의 호환성

| 팀 공동 사용 | 같은 절차와 기록 형식으로 테스트 진행 | 개별 동시 세션·이력 관리는 별도 설계

약 1,200개는 검사 항목 규모이며 고유 기능 수나 발견 결함 수가 아닙니다. 결과 XLSX가 만들어진 사실도 모든 항목의 통과나 최종 릴리즈 승인을 뜻하지 않습니다. 검사에서 관찰한 결과와 도구 개발 중 저장한 표본을 서로 다른 기록으로 유지했습니다.

### 2.2 Engineering Note

검사에서는 왜 기대와 달랐는지 구분해야 다음 조치가 정해졌고, 기록 도구에서는 같은 O 표시라도 적용 대상과 실제 사용 장비의 뜻이 달랐습니다. 검증의 품질은 판정을 많이 남기는 것보다, 그 판정이 어떤 조건과 관찰에서 나왔는지 보존하는 데 달려 있다는 점을 배웠습니다.
